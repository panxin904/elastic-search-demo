# DevOps 案例研究

5 个真实场景的工程决策剖析：电商大促、AI 推理发布、传统企业迁移、开源项目治理、金融强合规。

## 案例 1：电商大促的渐进式发布

**背景**：双 11 大促，新版本推荐算法需要上线，但算法可能引入性能 regression。

**方案**：
```
Phase 1 (T-7d)：影子流量压测
  - 100% 生产流量复制到 v2，观察 v2 延迟、错误率
  - 阈值：P99 < v1 * 1.2

Phase 2 (T-3d)：金丝雀 5%
  - 5% 真实流量
  - 监控 CTR（点击率）/ GMV（成交额）
  - 任何指标下降 > 2% 立即 abort

Phase 3 (T-1d)：金丝雀 20% → 50% → 100%
  - 每步观察 30 分钟
  - 自动 rollout Argo Rollouts

Phase 4 (T+1d)：保留旧版本 7 天
  - 出现问题秒级回滚
```

**结果**：算法版本成功发布，CTR +3.2%，P99 延迟无变化，回滚预案就绪。

## 案例 2：AI 推理服务的影子流量对比

**背景**：LLM 推理服务从 GPT-3.5 迁移到自研模型，需要对比响应质量。

**挑战**：
- 不能直接金丝雀（用户能感知响应质量差异）
- 不能 A/B（用户被分流会感知不公平）
- 需要大量真实流量才能对比质量

**方案**：影子流量
```
1. Envoy mirror 100% 生产流量到 v2
2. v2 只接收请求，不返回响应（响应丢弃）
3. 收集 v2 输出 → 离线评分（BLEU / 人工评分）
4. v2 质量 > v1 * 0.95 才考虑切流量
```

**结果**：1 周内对比 100 万条流量，确认自研模型质量达标后切换。

## 案例 3：传统企业迁移到 GitOps

**背景**：500 人研发团队，从 Jenkins + 手工部署 迁移到 GitLab CI + ArgoCD。

**挑战**：
- 团队习惯"SSH 到服务器 kubectl apply"
- 200+ 微服务的 manifest 散落
- 高管担心迁移风险

**方案（3 阶段）**：

```
Phase 1 (月 1-2)：影子模式
  - ArgoCD 同步 manifest 但 CI 不停
  - 验证 ArgoCD 工作流 + 团队培训
  - 成功指标：零生产事故

Phase 2 (月 3-4)：双写
  - 新服务走 GitOps，老服务维持现状
  - 成功指标：10 个新服务在 GitOps 下发布
  - 失败处理：发现问题立即回滚到 CI 控制

Phase 3 (月 5-6)：纯 GitOps
  - 全量服务切到 GitOps
  - 成功指标：DORA 部署频率提升 5 倍
```

**结果**：6 个月完成迁移，部署频率从 月 8 次 提升到 日 25 次，MTTR 从 4 小时 降到 30 分钟。

## 案例 4：开源项目的 CI/CD 治理

**背景**：Kubernetes 自身（5 万 star）的 PR 多达 200/天，CI 资源消耗巨大。

**挑战**：
- CI 运行时间长（提交到反馈 > 1 小时）
- 大量 PR 在排队（CI 资源不足）
- 维护者 review 负担重

**方案**：
```
1. 测试分层（必须 + 验证 + 完整）
   - 必须：lint + unit test（5 分钟）
   - 验证：lint + unit + integration（20 分钟）
   - 完整：必须 + 验证 + e2e + 性能（2 小时）

2. Prow（K8s 自己的 CI）
   - tide pool 自动合并（满足所有条件自动 merge）
   - 减少维护者 review 80% 的 trivial PR

3. 测试缓存 + 增量测试
   - 只跑被影响的包
   - bazel remote cache
```

**结果**：PR 平均反馈时间从 1 小时压到 15 分钟，CI 资源消耗降低 60%。

## 案例 5：金融强合规下的发布流程

**背景**：银行核心系统，等保 4 级 + 银保监合规，每次发布需要完整审计。

**挑战**：
- 每次发布必须人工审批（合规要求）
- 审计日志必须保留 5 年
- 任何变更需要可追溯到具体人

**方案**：
```
1. 四眼原则（Two-person rule）
   - Developer PR → Tech Lead Approve → Security Approve → Deploy
   - 每个环节自动记录操作者 + 时间 + IP

2. 不可变基础设施
   - 所有环境用镜像部署（每次发布 = 新镜像）
   - 镜像 SBOM + Cosign 签名入审计

3. 应急通道
   - 紧急情况可以"破窗"跳过审批
   - 但必须在 24 小时内补完整审计流程
   - 破窗率作为 KPI 监控（> 5% 触发审查）
```

**结果**：合规审计 100% 通过，发布频率从 月 2 次 提升到 周 1 次（合规限制下的最优解）。
