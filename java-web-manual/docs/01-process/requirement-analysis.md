# 需求分析

拿到需求后的第一步，决定了后续所有工作的方向和质量。

## 需求分析五步法

### 第一步：理解业务背景

<div class="kg-note">
<strong>不要一上来就想技术方案</strong>，先搞清楚：这个需求要解决什么业务问题？涉及哪些用户角色？业务流程是什么？
</div>

关键问题清单：
- 这个需求解决什么问题？（用户痛点）
- 涉及哪些角色？（用户、管理员、第三方）
- 核心业务流程是什么？（画流程图）
- 有没有参考系统？（竞品分析）

### 第二步：梳理功能清单

将需求拆解为功能点，按优先级排列：

```markdown
## 需求：用户下单功能

### P0（必须做）
- 用户选择商品加入购物车
- 提交订单（含收货地址）
- 生成订单号，记录订单状态

### P1（应该做）
- 订单列表分页查询
- 订单状态变更通知

### P2（可以做）
- 订单导出 Excel
- 推荐相关商品
```

### 第三步：确认边界条件

<div class="kg-note kg-note-warning">
边界条件是最容易被忽略的地方，却是 bug 高发区。
</div>

| 边界 | 需要确认的问题 |
|---|---|
| 数据边界 | 最大下单数量？金额范围？字符长度？ |
| 状态边界 | 哪些状态之间可以流转？哪些不行？ |
| 并发边界 | 同一用户能否同时下多个单？库存扣减怎么处理？ |
| 异常边界 | 支付超时怎么办？网络断开怎么办？ |
| 时间边界 | 是否需要定时任务？有效期？ |

### 第四步：确认验收标准

> 什么叫"做完了"？必须和产品经理/需求方达成共识。

```yaml
验收标准示例:
  功能: 用户下单
  验收:
    - 用户可选择商品、填写地址、提交订单
    - 库存不足时提示用户，订单不生成
    - 订单状态从"待支付"变为"已支付"
    - 支付超时 30 分钟后自动取消订单
    - 订单列表支持按状态筛选和分页
```

### 第五步：评估与排期

| 维度 | 评估内容 |
|---|---|
| 前端工作量 | 页面数、组件复杂度、交互逻辑 |
| 后端工作量 | 接口数、业务复杂度、数据模型 |
| 依赖项 | 需要哪些上游提供接口/数据？ |
| 风险点 | 技术难点、第三方依赖、人力风险 |

## 需求分析文档模板

```markdown
# [需求名称] 需求分析文档

## 1. 业务背景
## 2. 功能范围

  - P1（重要）:
  - P2（可选）:
## 3. 流程图
## 4. 边界条件
## 5. 验收标准
## 6. 依赖与风险
## 7. 预估排期
```
