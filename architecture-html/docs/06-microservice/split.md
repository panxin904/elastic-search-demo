# 服务拆分原则

## 1. 为什么拆

```
单体：所有功能在一个进程
  ✅ 简单（部署 / 调试 / 事务）
  ❌ 任何修改要全量发布
  ❌ 一个慢调用拖垮整个进程
  ❌ 团队大 = 互相阻塞

微服务：按业务能力拆分
  ✅ 独立发布（10 个服务可以并行 10 个团队）
  ✅ 独立扩容（订单高峰只扩订单服务）
  ❌ 分布式事务复杂
  ❌ 调用链追踪难
```

## 2. 拆分的 3 个维度

### DDD（推荐）

按**限界上下文（Bounded Context）**拆：
- 订单上下文（OrderContext）：订单、支付、物流
- 商品上下文（CatalogueContext）：商品、类目、库存
- 用户上下文（IdentityContext）：用户、认证、权限

每个上下文 = 一个服务（或多个聚合服务）。

### 康威定律

> "设计系统的组织，受限于沟通结构"

团队结构 = 系统结构。微服务团队 = 2 个披萨团队（4-7 人）。

### 业务能力

按业务能力拆（识别 + 分解），不是按技术层（web / service / dao）。

## 3. 拆分原则

### 单一职责（Single Responsibility）

一个服务 = 一个业务能力。

```
❌ UserService 包含：注册/登录/订单/支付/物流/推荐/搜索/...
✅ UserService：只管用户
✅ OrderService：只管订单
✅ PaymentService：只管支付
```

### 自治性

每个服务能独立：
- 部署（独立 release）
- 扩缩（独立 HPA）
- 选型（不同语言/数据库）
- 失败（一个挂不影响其他）

### 边界清晰

服务间调用通过 API（不要共享数据库表，不要直连对方的 DB）。

## 4. 拆分粒度

```
原则：先粗后细（演进式拆分）

V1: 单体
V2: 按业务领域拆（5-10 个服务）
V3: 按限界上下文拆（10-30 个）
V4: 按聚合拆（30+ 个）

过早拆分 = 分布式复杂度爆炸
过晚拆分 = 耦合拖垮迭代
```

**判断标准**：
- 团队规模（10+ 人开始拆）
- 部署频率（每日 N 次发布就该拆）
- 性能瓶颈（某模块特别慢独立扩容）

## 5. 拆分模式

### 绞杀者（Strangler Fig）

```
旧单体 ← 流量渐渐切到 → 新服务
  订单服务 API     →   OrderService（独立部署）
  用户管理 API     →   UserService
  ... 慢慢全部迁移
```

**优点**：渐进式迁移，不需 big-bang 重写。

### 共享内核（Shared Kernel）

最初阶段：同一团队的微服务**共享部分代码**（domain model、工具类），避免过早抽象。

### 数据库拆分

```
初始：共享一个 database，每个服务一组表
演进：每服务一个 schema → 每服务一个 database

database 拆分 = 终极拆分
避免"分布式单体"（每服务一个 DB，但表 join 满天飞）
```

## 6. 反模式

- **分布式单体**：服务拆了但 API 互相同步调用（链路长 = 慢 + 难调试）
- **共享数据库**：服务拆了但表 join
- **过早拆分**：3 人团队拆 5 个服务
- **按层拆**：Web / Service / DAO → 不是微服务
- **按数据表拆**：UserDB / OrderDB → 边界是表不是业务

## 7. 拆分流程（实战）

```
1. 业务梳理（事件风暴 / 用户旅程）
2. 识别限界上下文（DDD）
3. 定义上下文地图（聚合关系）
4. 优先拆最痛的地方（改得最频繁 / 故障最多）
5. Strangler：旧单体中抽出 → 新服务 → 切流量
6. 数据逐步迁移（双写 → 切读 → 切写）
7. 重复直到满意
```

## 8. 实战 checklist

```
- [ ] 服务边界按业务能力，不按技术层
- [ ] 每个服务 ≤ 5 个队友接口
- [ ] 数据自治（每服务自己 DB）
- [ ] 跨服务调用走 API（不是直接查 DB）
- [ ] 团队规模 ≤ 8 人 / 服务
- [ ] 服务发布独立（独立版本号）
- [ ] 关键路径有 fallback
- [ ] 有服务目录 / 注册中心
```
