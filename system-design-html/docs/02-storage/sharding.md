# 数据分片策略

> 当单台机器存不下、扛不住时，把数据**水平切分**到多台机器上。

## 1. 为什么需要分片？

```
单机的瓶颈：
  - 容量：硬盘 TB 级就到顶
  - QPS：单实例 1-10 万
  - 网络：单机带宽有限

分片的目标：
  - 容量：N × 单机容量
  - QPS：N × 单机 QPS
  - 单点故障：部分节点挂不影响全局
```

## 2. 分片 vs 复制

```
分片（Sharding / Partitioning）：
  - 同一份数据切多片，存不同机器
  - 每片只存一部分数据
  - 目的：扩展容量与 QPS

复制（Replication）：
  - 同一份数据存多份
  - 每台机器都有完整 / 部分副本
  - 目的：高可用 + 读扩展

📌 大部分系统是 分片 + 复制 组合：
   - 先分片（每片只存一部分）
   - 每片再复制多副本（高可用）
```

## 3. 分片策略

### 3.1 按哈希分片（Hash Sharding）

```
key → hash(key) → hash % N → 节点编号

例：
  hash("user_10086") = 12345678
  12345678 % 4 = 2  →  分到节点 2

优点：
  - 数据分布均匀
  - 写入无热点（理论）

缺点：
  - 范围查询要扫所有节点
  - 扩容时数据迁移量大（N 变 N+1，几乎全部数据要重分布）

典型系统：
  - Redis Cluster
  - DynamoDB（部分）
  - Cassandra
```

### 3.2 按范围分片（Range Sharding）

```
按 key 的范围切分：
  [A-G] → 节点 1
  [H-N] → 节点 2
  [O-T] → 节点 3
  [U-Z] → 节点 4

优点：
  - 范围查询高效（连续 key 在同节点）
  - 扩容友好（只迁移部分范围）

缺点：
  - 热点问题（最新数据集中在尾部节点）

典型系统：
  - HBase
  - TiDB
  - BigTable
  - MongoDB（可配置）
```

### 3.3 按一致性哈希（Consistent Hashing）

```
把哈希空间组织成环：
  key → 顺时针找到的第一个节点

优点：
  - 扩容只影响相邻节点（迁移量小）
  - 节点异构友好（每节点负责不同范围）

缺点：
  - 实现稍复杂
  - 仍可能数据倾斜（解决：虚拟节点）

典型系统：
  - Dynamo / DynamoDB
  - Cassandra
  - Akamai CDN

📌 单独写：[一致性与虚拟节点](./consistent-hash.md)
```

### 3.4 按目录分片（Directory-based Sharding）

```
维护一张分片表：
  user_id 1-1000     →  shard 0
  user_id 1001-5000  →  shard 1
  ...

优点：
  - 灵活（可任意规则分片）
  - 业务可自定义

缺点：
  - 元数据单点
  - 分片表自身需要高可用

典型系统：
  - 早期 Google GFS / BigTable 雏形
  - 业务自实现
```

## 4. 分片键的选择

### 4.1 分片键（Shard Key）的要求

```
1. 高基数（High Cardinality）：
   - 值域大（用户 ID、订单 ID）
   - 避免低基数（性别、状态）

2. 均匀分布（Even Distribution）：
   - 避免热点（时间戳 → 全部写到最新节点）
   - 业务上做"打散"（加随机后缀）

3. 查询友好（Query-Friendly）：
   - 常用查询条件包含分片键
   - 避免跨分片查询
```

### 4.2 反例：为什么不用时间戳分片？

```
按 created_at 分片：
  2026-08-01 ~ 2026-08-31 → shard_202608
  2026-09-01 ~ 2026-09-30 → shard_202609

问题：
  - 写入全部集中到最新分片
  - 历史分片几乎无写入（浪费）
  - 扩容难（新增月分片后还要再分旧数据）
```

### 4.3 反例：为什么不用状态分片？

```
按 status 分片：
  pending 订单 → shard_a
  paid 订单    → shard_b
  shipped 订单 → shard_c

问题：
  - pending 是少数，shard_a 一直空闲
  - paid/shipped 长期累积，shard_b/c 压力大
  - 不同状态之间还要数据迁移
```

## 5. 跨分片查询

### 5.1 什么是跨分片查询？

```
SELECT * FROM orders WHERE user_id = 10086 AND status = 'paid'

如果按 user_id 分片：
  - 只需查一个分片 ✓

如果按 created_at 分片：
  - 要查所有分片 ✗
  → 性能灾难
```

### 5.2 解决：组合分片 / 二级索引

```
方案 1：组合分片键
  shard_key = (user_id, created_at)
  优点：单分片完成查询
  缺点：写入时必须带 user_id

方案 2：全局二级索引
  单独维护一张 status → user_id 索引表
  优点：灵活
  缺点：写入双倍 + 索引自身要分片

方案 3：宽表（反范式）
  一次写入预聚合（订单宽表 + 用户状态宽表）
  优点：查询快
  缺点：写入复杂
```

## 6. 扩容：Rebalance

### 6.1 哈希分片的痛点

```
N=3 扩到 N=4：
  原本在节点 i 的数据：
    hash(key) % 3 = i
  新公式：
    hash(key) % 4 = i'
  → 大部分 key 的 i' ≠ i
  → 几乎所有数据要重哈希 + 迁移

📌 N 越大迁移比例越高（N → N+1，约 N/(N+1) 数据迁移）
```

### 6.2 一致性哈希的优雅

```
增加节点 D：
  - 只影响 A → D 之间的 key
  - 其他节点完全不动
  → 迁移量 = 1/N（理论）

📌 这就是为什么 Dynamo / Cassandra 选一致性哈希
```

### 6.3 工程上的双写 + 灰度迁移

```
不能直接停机迁移：
  1. 双写：新老分片都写
  2. 回填：异步把老数据搬到新分片
  3. 校验：检查双写一致性
  4. 切读：把读流量切到新分片
  5. 清理：删除老分片

📌 这就是 Stripe / Uber 公开分享的"零停机迁移"流程
```

## 7. 热点问题

### 7.1 热点是什么？

```
某分片 QPS 远高于其他分片
  - 网红直播打赏 → 该主播的所有写入集中在一个分片
  - 秒杀爆款 → 该商品库存写入集中

后果：
  - 单分片压力过大
  - 拖垮整个系统
```

### 7.2 解决：打散 + 本地缓存

```
方案 1：随机后缀
  user_id + random(0-99) 作为分片键
  读时按 user_id 查所有 100 个分片，合并
  → 写入压力分散到 100 个分片

方案 2：本地缓存
  热点商品库存写在 Redis 本地内存
  不走分布式存储
  → 单机扛住热点

方案 3：热点探测
  自动检测热点 key
  动态把热点 key 复制到更多分片
```

## 8. 一句话总结

```
📌 分片是为了扩展容量 + QPS，不是为了高可用（那是复制的职责）
📌 哈希分片：均匀但扩容难；范围分片：灵活但有热点；一致性哈希：折中
📌 分片键三原则：高基数、均匀分布、查询友好
📌 跨分片查询很贵：用组合分片键或全局二级索引
📌 扩容不能停机：双写 + 灰度 + 校验 + 切读 + 清理
📌 热点问题需要运行时探测，单纯分片解决不了
```
