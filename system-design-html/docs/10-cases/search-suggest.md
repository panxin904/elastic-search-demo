# 搜索建议系统

> 用户输入"ja"，提示"javascript / java / json"。**实时 + 准确 + 性能**。

## 1. 什么是搜索建议？

```
场景：
  Google / 百度搜索框
  - 用户输入前缀
  - 系统返回热门补全
  - 实时更新（输入即返回）

形式：
  - 前缀补全（"ja" → "javascript"）
  - 拼写纠错（"javascrpt" → "javascript"）
  - 个性化（"苹果" → 用户历史偏好）
```

## 2. 核心要求

```
1. 低延迟：
   - 每次按键都要返回
   - P99 < 100ms

2. 准确：
   - 补全要相关
   - 不要返回乱码

3. 实时：
   - 热点变化要反映
   - 热门搜索要及时

4. 高可用：
   - 不能因为建议挂导致搜索也挂
   - 建议失败要兜底
```

## 3. 整体架构

```
用户输入 "ja"
       ↓
前端 debounce + 限流
       ↓
API 网关
       ↓
建议服务
       ↓
  ┌────┼────┐
  ↓    ↓    ↓
Trie  ES  Redis
（前缀） （热词）（缓存）

返回 Top N 补全
```

## 4. 前缀树（Trie）

### 4.1 数据结构

```
Trie（字典树）：
  - 每个节点是一个字符
  - 路径 = 单词
  - 末端节点存关联数据（如频次）

例：建索引 ["javascript", "java", "json", "jar"]

            root
           / | \
          j  ...
         /|\
        a  s  ...
       /|\  \
      v  r  o
     /   |   \
    a   (*)  n
   / \        \
  s  (*)      (*)
 / \
c  (*)
 \
  r
   \
   ipt
    \
    (*)

带 (*) 是单词结尾
```

### 4.2 查询流程

```
输入 "ja"：
  1. 从 root 走 j → a
  2. 收集所有以 "ja" 开头的单词
  3. 按频次排序
  4. 返回 Top N

复杂度：
  - 查找：O(L)，L = 前缀长度
  - 收集：O(K)，K = 候选词数
```

### 4.3 实现方案

```
方案 1：内存 Trie
  - 启动时构建
  - 全部在内存
  - 适合词典规模小（< 10 万）

方案 2：前缀树数据库
  - Redis / RocksDB
  - 支持持久化

方案 3：第三方库
  - Lucene PrefixQuery
  - ES completion suggester
```

### 4.4 中文 Trie

```
中文问题：
  - 没有空格分词
  - 必须先分词
  - "苹果手机" → "苹果" + "手机"

方案：
  - IK / jieba 分词
  - 把每个词加入 Trie
  - 查询时也分词查询
```

## 5. 编辑距离（拼写纠错）

### 5.1 算法

```
Levenshtein 距离：
  - 字符替换 / 插入 / 删除的最少操作数

例：
  "javascrpt" → "javascript"
  差 1 个字符（插入 'i'）
  距离 = 1

动态规划：
  dp[i][j] = word1[0..i] → word2[0..j] 的最小操作

  if word1[i] == word2[j]:
      dp[i][j] = dp[i-1][j-1]
  else:
      dp[i][j] = min(
          dp[i-1][j-1] + 1,  # 替换
          dp[i-1][j] + 1,    # 删除
          dp[i][j-1] + 1     # 插入
      )
```

### 5.2 在建议中的应用

```
"javascrpt" 的建议：
  1. 计算每个候选词的编辑距离
  2. 距离 ≤ 2 的候选
  3. 按距离 + 频次排序

候选：
  - "javascript"（距离 1，频次高）
  - "typescript"（距离 5，过滤）
  → "javascript" 返回
```

### 5.3 性能优化

```
朴素实现：O(M × N) 每个候选都算距离
优化：
  - 预计算词频 + 长度，过滤不可能的
  - BK-tree（编辑距离索引）
  - 提前终止（距离超阈值）
```

## 6. 热词与个性化

### 6.1 全网热词

```
数据来源：
  - 搜索日志（过去 N 分钟）
  - 排序：搜索量 / 点击率

存储：
  - Redis Sorted Set：ZINCRBY 更新
  - 定期 dump 到 DB

查询：
  - 前缀匹配后，按热度排序
  - 热门词排在前面
```

### 6.2 用户个性化

```
个性化建议：
  - 用户搜索历史
  - 用户兴趣标签
  - 地理位置（本地搜索）

实现：
  - 用户特征存储（HBase / Redis）
  - 查询时合并
  - LLM 推荐（现代方案）

📌 个性化会引入隐私问题
   要注意合规
```

### 6.3 上下文感知

```
"苹果"：
  - 在 3C 类目下 → 苹果手机 / 电脑
  - 在 水果类目下 → 苹果水果
  - 在电影类目下 → 苹果电影

实现：
  - 类目 + 关键词联合索引
  - 用户当前类目优先
```

## 7. 工程实现

### 7.1 离线构建

```
定时任务：
  - 从搜索日志聚合热词
  - 加载到 Redis
  - 更新 Trie 缓存

频率：
  - 短词（1-3 字）：1 分钟
  - 长词（4+ 字）：5 分钟
```

### 7.2 在线查询

```
查询路径：
  1. 前端输入 → API
  2. 服务查 Trie / Redis
  3. 合并 + 排序
  4. 返回 Top 10

性能：
  - 内存查询 < 1ms
  - Redis 查询 < 5ms
  - ES 查询 < 50ms
```

### 7.3 缓存策略

```
多级缓存：
  - L1：本地缓存（热门前缀）
  - L2：Redis（前缀结果）
  - L3：ES（完整搜索）

过期：
  - 热词缓存：5 分钟
  - 个性化缓存：1 小时
```

## 8. ES completion suggester

```
ES 自带 completion suggester：

  POST /products/_search
  {
    "suggest": {
      "product_suggest": {
        "prefix": "jav",
        "completion": {
          "field": "title_suggest",
          "size": 10
        }
      }
    }
  }

优点：
  - 基于 FST（Finite State Transducer）
  - 内存索引，毫秒级响应
  - 支持上下文过滤

缺点：
  - 需要重建索引
  - 更新有延迟
```

## 9. LLM 时代的搜索建议

```
传统方案 vs LLM：

传统：
  - 输入前缀 → 返回固定列表
  - 依赖词典 + 热词

LLM：
  - 输入前缀 + 上下文 → 生成建议
  - 个性化更强

实现：
  - LLM 推理（API 调用）
  - 延迟 200-500ms
  - 不能按键即返回（按回车时调用）

混合方案：
  - 输入时：传统 Trie + 热词（即时）
  - 提交时：LLM 增强（深度）
```

## 10. 经典面试题

### 10.1 前缀搜索

```
Q：设计搜索建议
A：
  1. Trie 树存词典（内存）
  2. Redis 存热词
  3. ES completion suggester（兜底）
  4. 多级缓存
  5. 个性化（用户画像）

追问：中文怎么处理？
  - 分词后建 Trie
  - 或直接用 ES 中文分词
  
追问：怎么支持拼写纠错？
  - 编辑距离
  - BK-tree 加速
```

### 10.2 高并发

```
Q：100 万 QPS 搜索建议
A：
  - CDN 缓存（不变的前缀）
  - Redis Cluster 分片
  - 本地缓存（热前缀）
  - 异步热词更新

追问：缓存一致性？
  - 短 TTL（5 分钟）
  - 失效即可（建议可容忍旧）
  
追问：怎么降级？
  - Trie 不可用 → 返回热门
  - Redis 不可用 → 返回静态建议
```

## 11. 一句话总结

```
📌 搜索建议 = Trie（前缀）+ 编辑距离（纠错）+ Redis（热词）+ 个性化
📌 Trie 查询 O(L)，适合词典规模 10 万级
📌 编辑距离：Levenshtein 算法，O(M × N)
📌 热词：Redis ZINCRBY 实时计数，定期 dump
📌 个性化：用户画像 + 上下文 + LLM 增强
📌 工程方案：ES completion suggester（基于 FST，毫秒级）
📌 性能：多级缓存 + 异步热词 + 按键延迟（debounce）
📌 LLM 时代：按键用传统，提交用 LLM 增强
```
