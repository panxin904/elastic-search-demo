# 秒杀系统设计

> 几万人在同一秒抢几百件商品。**避免超卖 + 高并发 + 用户体验**。

## 1. 秒杀的核心难题

```
  1 件商品，10 万人抢，库存 100 件
  → 必须保证：
     - 不超卖（库存 ≥ 0）
     - 不漏卖（库存尽量卖完）
     - 不宕机（不能被流量冲垮）
     - 用户体验（不要等太久）

📌 三大目标：
   库存正确性（业务约束）
   系统可用性（技术约束）
   公平性（业务约束）
```

## 2. 整体架构

```
                客户端
                   ↓ (拦截 99%)
              CDN / 静态化
                   ↓
            网关（限流 / 风控）
                   ↓
            秒杀服务（核心）
          ┌────┼────┐
          ↓    ↓    ↓
       Redis  MQ   DB
       (库存) (订单) (订单)
```

## 3. 关键设计

### 3.1 前端：拦截 99% 流量

```
1. 静态化：
   - 秒杀页面静态化（HTML 推 CDN）
   - CDN 抗 90% 流量

2. 按钮防抖：
   - 点击后按钮置灰
   - 防止重复提交

3. 验证码 / 滑块：
   - 拦截机器人
   - 削峰（验证耗时 1-2s）

4. 排队提示：
   - "前方有 5000 人排队"
   - 用户感知"系统在努力"
   - 心理缓冲

📌 前端能做的事不要留给后端
```

### 3.2 网关：限流 + 风控

```
限流维度：
  - IP：每 IP 每秒 10 次
  - 用户：每用户每秒 1 次
  - 全局：10000 QPS 上限

风控规则：
  - 新注册用户不让秒
  - 黑名单用户直接拦截
  - 同一设备多账号拦截

策略：
  - 超限 → 返回"系统繁忙"
  - 风控命中 → 验证码升级
```

### 3.3 秒杀服务：Redis 预扣库存

```
核心思路：
  1. 库存预加载到 Redis（int 类型）
  2. 扣减用 Lua 原子操作
  3. 异步同步到 DB
```

### 3.4 Redis Lua 原子扣库存

```lua
-- KEYS[1]: stock_key
-- ARGV[1]: user_id
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock <= 0 then
    return -1  -- 没库存
end

-- 防止重复抢购（用户维度）
local bought_key = "seckill_bought:" .. KEYS[1] .. ":" .. ARGV[1]
if redis.call('SISMEMBER', bought_key, ARGV[1]) == 1 then
    return -2  -- 已抢购
end

-- 扣减
redis.call('DECR', KEYS[1])
redis.call('SADD', bought_key, ARGV[1])
return 1  -- 成功
```

```
原子性：
  - Lua 脚本在 Redis 单线程执行
  - 整个脚本原子
  → 不超卖 + 不重复抢
```

### 3.5 异步下单

```
Redis 扣减后：
  1. 写一条消息到 MQ（订单创建）
  2. 直接返回"排队中"给用户
  3. 后台 worker 消费 MQ：
     - 创建订单
     - 扣 DB 库存（一致性兜底）
     - 发短信通知

📌 用户不阻塞在同步等待
```

## 4. 库存同步

```
Redis 是"快速通道"，DB 是"权威"

  Redis          DB
  库存 100       库存 100
     ↓ 扣减 1
  库存 99
     ↓ 异步同步
                库存 99

不一致场景：
  - Redis 扣减成功，MQ 消息丢失 → DB 未扣
  - 解决：定期对账 + 自动补扣

一致性策略：
  - Redis 扣减 = 预扣
  - DB 扣减 = 真实扣减
  - 以 DB 为准，Redis 是性能优化
```

## 5. 超卖与少卖

### 5.1 超卖

```
原因：
  - Redis Lua 没写好（非原子）
  - Redis 扣减成功但 DB 未扣减（异步丢失）
  - 多实例并发扣减（理论不会，因为 Redis 单线程）

解决：
  - Redis Lua 原子扣减（防止超卖）
  - DB 唯一索引兜底（订单重复插入会失败）
  - 定期对账 + 补偿
```

### 5.2 少卖

```
原因：
  - MQ 消息丢失（Redis 扣了但没下单）
  - DB 同步失败

解决：
  - MQ 重试
  - 定时对账
  - 库存回收（DB 库存 > Redis 库存时调整）
```

## 6. 风控

```
黄牛识别：
  - 新注册账号
  - 同一设备多账号
  - 抢购频率异常

策略：
  - 账号注册时间 < N 天 → 加验证码
  - 设备 ID 已购买 → 拦截
  - 同一 IP 多次下单 → 加验证码

机器流量识别：
  - 滑块 / 验证码
  - 行为分析（鼠标轨迹）
  - IP 频率
```

## 7. 流量分层

```
第一层：拦截 90% 流量
  - 静态化 + CDN
  - 网关限流

第二层：拦截 99% 流量
  - 风控规则
  - 验证码

第三层：秒杀服务
  - Redis Lua 原子
  - 异步下单

第四层：DB
  - 兜底（正常不会到）

📌 一层一层拦截，DB 是最后的堡垒
```

## 8. 灾备与降级

### 8.1 灾备

```
多机房：
  - 主机房 + 灾备机房
  - DNS 切流
  - Redis 主从 + 跨机房同步

限流降级：
  - Redis 挂 → 返回"系统维护中"
  - MQ 挂 → 直接写 DB（兜底，但慢）
  - DB 挂 → 返回"请重试"
```

### 8.2 降级开关

```
准备好的开关：
  - 关闭非核心功能
  - 返回静态"秒杀结束"
  - 直接拒绝所有请求

触发条件：
  - Redis 库存查询 > 1s
  - MQ 堆积 > 10 万
  - DB QPS > 阈值
```

## 9. 经典面试题：抢购流程

```
Q：设计秒杀系统
A：
  1. 前端：CDN + 防抖 + 验证码
  2. 网关：限流 + 风控
  3. 秒杀服务：Redis Lua 原子扣库存
  4. MQ 异步下单
  5. DB 兜底：定时对账
  
追问：怎么防止超卖？
  - Redis Lua 原子 + DB 唯一索引双保险
  
追问：MQ 挂了怎么办？
  - 降级为同步写 DB（慢但能下单）
  - 或返回"系统繁忙，请重试"
  
追问：Redis 挂了怎么办？
  - 拒绝所有请求
  - 或降级为直接读 DB（限流）
```

## 10. 经典面试题：库存预热

```
Q：怎么预热库存？
A：
  - 秒杀开始前（如 1 分钟）：
    - 从 DB 加载库存到 Redis
    - SET stock:sku_123 100
  - 秒杀开始：直接用 Redis 库存
  - 秒杀结束：剩余库存回写 DB

追问：Redis 库存怎么同步到 DB？
  - 异步 worker 消费 MQ
  - 实时性不强（最终一致）
  
追问：Redis 和 DB 库存不一致怎么办？
  - 定期对账脚本
  - 以 DB 为准，Redis 是预扣
```

## 11. 一句话总结

```
📌 秒杀 = 前端拦截 + 网关限流 + Redis Lua 原子扣减 + MQ 异步下单 + DB 兜底
📌 关键：Redis Lua 原子（不超卖）+ MQ 异步（不阻塞用户）+ DB 兜底（最终一致）
📌 风控：黄牛识别 + 验证码 + 行为分析
📌 灾备：多机房 + 限流降级 + 开关预案
📌 性能：库存预热 + 静态化 + CDN 抗 90% 流量
📌 一致性：以 DB 为准，Redis 是预扣（最终一致）
📌 经典：阿里双 11 / 京东 618 都是这套架构
```
