# Feed 流系统设计

> 关注、被关注、被推荐的内容聚合流。推模式 vs 拉模式 vs 混合模式。

## 1. 什么是 Feed 流？

```
典型场景：
  - 朋友圈（关注流）：看到所有好友动态
  - 微博：关注流 + 推荐流
  - 抖音：纯推荐流（不关注任何人）
  - B 站：关注流 + 推荐流 + 分区流

本质：
  - 用户 N 看到的"内容列表"
  - 内容按时间 / 兴趣 / 算法排序
  - 实时更新（新内容进来）
```

## 2. 核心难点

```
1. 写入扩散 vs 读取聚合：
   - 写入：一个用户发帖子
   - 读取：100 万粉丝都看到这个帖子
   - 写入扩散（推）或读取聚合（拉）？

2. 时间排序：
   - 最新的在最前
   - 关注的多个用户的帖子混排

3. 大 V 性能：
   - 1 亿粉丝的大 V 发帖
   - 推给 1 亿粉丝 = 1 亿次写
   - 拉的方案 = 每个粉丝读时聚合 100 个关注列表

4. 个性化推荐：
   - 不是关注流而是推荐流
   - 算法 + 实时计算
```

## 3. 三种核心模式

### 3.1 推模式（Push / Fan-out on Write）

```
发帖时推给所有粉丝：

用户发帖 → 写自己的发件箱
        → 写入所有粉丝的收件箱

读时：直接读自己的收件箱

┌─────────────┐
│ 用户发帖    │
└──────┬──────┘
       │ 写入
       ↓
┌──────────────────────────────────┐
│ 收件箱（每用户一个）              │
│ user_1 → [post_a, post_c, ...]  │
│ user_2 → [post_a, post_d, ...]  │
│ user_3 → [post_a, post_e, ...]  │
│ ...                              │
└──────────────────────────────────┘

读：user_X 看自己收件箱即可

📌 优点：读快（O(1)）
📌 缺点：写慢（大 V 写扩散）+ 存储浪费（重复存）
```

### 3.2 拉模式（Pull / Fan-out on Read）

```
发帖时只写自己的发件箱：
  - 用户发件箱存所有自己发的帖子
读时：聚合所有关注对象的发件箱

┌──────────────┐     ┌──────────────┐
│ user_A 收件箱│     │ user_B 收件箱│
│ post_1       │     │ post_2       │
│ post_5       │     │ post_3       │
└──────────────┘     └──────────────┘

读 user_X 时：
  - 找出 user_X 关注的所有用户
  - 读这些用户的发件箱
  - 合并排序（按时间）
  - 分页返回

📌 优点：写快（O(1)）
📌 缺点：读慢（聚合 N 个发件箱）
```

### 3.3 混合模式（Hybrid）

```
普通用户用推，大 V 用拉：

判断用户粉丝数：
  - < 1000：用推
  - ≥ 1000：用拉
  → 平衡读写性能

读时：
  - 推用户：直接读收件箱
  - 拉用户：聚合发件箱
  → 合并返回
```

## 4. 架构对比

```
┌──────────────┬──────────────────┬──────────────────┬──────────────────┐
│              │ 推模式           │ 拉模式           │ 混合模式         │
├──────────────┼──────────────────┼──────────────────┼──────────────────┤
│ 写入复杂度   │ O(粉丝数)        │ O(1)             │ 视情况           │
│ 读取复杂度   │ O(1)             │ O(关注数)        │ 视情况           │
│ 存储         │ 大量重复         │ 较少             │ 中等             │
│ 实时性       │ 高（已聚合）     │ 低（读时聚合）   │ 中               │
│ 大 V 性能    │ 差               │ 好               │ 好               │
│ 实现复杂度   │ 中               │ 中               │ 高               │
│ 适用         │ 中小规模         │ 大规模           │ 大规模           │
│ 代表         │ 朋友圈（早期）   │ 抖音（推荐流）   │ Twitter          │
└──────────────┴──────────────────┴──────────────────┴──────────────────┘
```

## 5. 推模式的实现细节

### 5.1 异步扩散

```
发帖同步流程：
  1. 写入自己发件箱
  2. 发 MQ 消息
  3. 返回成功给客户端

后台 worker：
  1. 消费 MQ 消息
  2. 查粉丝列表（按 shard 切分）
  3. 写入每个粉丝收件箱
  → 不阻塞发帖
```

### 5.2 消息队列选型

```
Kafka：
  - 高吞吐
  - 分区保证顺序
  - 适合扩散任务

RocketMQ：
  - 支持事务消息
  - 适合需要事务一致的场景
```

### 5.3 收件箱结构

```
Redis Sorted Set：
  - score = 时间戳
  - value = 帖子 ID
  - ZADD：推时写入
  - ZRANGE：读时拉取
  - ZREMRANGEBYRANK：裁剪旧帖子

容量：1000-5000 条
裁剪：超过容量上限裁剪旧帖子
```

### 5.4 大 V 限流

```
粉丝数 > 100 万的用户：
  - 异步扩散（不阻塞发帖）
  - 限流（每秒最多 X 个粉丝）
  - 失败重试
  - 部分失败容忍（个别粉丝没收到）
```

## 6. 拉模式的实现细节

### 6.1 发件箱结构

```
用户发件箱：
  - 列表：自己发的所有帖子（按时间排序）
  - 单机：MySQL / PostgreSQL
  - 分布式：按用户 ID 分片

容量：通常无上限（或很大）
裁剪：很少裁剪（用户可以删除）
```

### 6.2 关注列表

```
用户关注列表：
  - Set 结构（Redis）
  - 关注数：100-1000

读 Feed 时：
  - 找出关注的所有用户
  - 读这些用户的发件箱
  - 合并排序
```

### 6.3 多路归并

```
读 user_X 的 Feed：
  1. 取出关注列表 [A, B, C, D, ...]
  2. 对每个关注对象的发件箱取前 N 条
  3. 多路归并（按时间）
  4. 返回前 K 条

📌 时间复杂度：O(M log K)
   M = 关注数
   K = Feed 长度

优化：分页游标 + 缓存
```

## 7. 混合模式详解

### 7.1 Twitter 的实现

```
判定用户类型：
  - 粉丝数 < 阈值 → 推（fanout-on-write）
  - 粉丝数 ≥ 阈值 → 拉（fanout-on-read）

读时合并：
  - 推部分：直接读收件箱
  - 拉部分：聚合大 V 发件箱
  - 合并排序
```

### 7.2 关注度区分

```
强关注 vs 弱关注：
  - 互关好友 → 强关注（推）
  - 关注的大 V → 弱关注（拉）
  → 不同路径不同优化
```

## 8. 时间排序

### 8.1 全局时间 vs 个性化时间

```
全局时间：
  - 所有用户看到相同的"时间戳"
  - 推模式天然支持

个性化时间：
  - 不同用户看到不同的顺序
  - 考虑互动（点赞、评论）、关注度
  - 推荐算法
```

### 8.2 时间衰减

```
热门 Feed：
  - 初始按时间排
  - 加入"热度"分数（点赞、评论、转发）
  - 随时间衰减
  → 综合分数排序

例：
  score = 0.7 * 时间因子 + 0.3 * 热度因子
```

## 9. 推荐 Feed

### 9.1 触发模型

```
召回（Recall）：
  - 从内容池取候选
  - 关注流 / 热门 / 算法 / 标签

粗排（Pre-rank）：
  - 简单模型打分
  - 过滤低质内容

精排（Rank）：
  - 复杂模型
  - 实时特征 + 离线特征

重排（Re-rank）：
  - 多样性 / 去重
  - 业务规则
```

### 9.2 实时推荐

```
用户操作 → 实时特征更新 → 模型预测 → 调整 Feed

📌 实时计算（Flink / Spark Streaming）
   - 用户特征实时更新
   - 内容特征实时计算
   - 模型在线推理
```

## 10. 存储选型

### 10.1 收件箱（推模式）

```
Redis Sorted Set：
  - 每用户一个 Sorted Set
  - 容量限制（裁剪旧内容）
  - LRU 缓存热数据

冷数据：
  - HBase / ClickHouse
  - 历史 Feed 归档
```

### 10.2 发件箱（拉模式）

```
MySQL / TiDB：
  - 按用户 ID 分片
  - 按时间索引
  - 支持复杂查询

Redis Cache：
  - 热门用户的发件箱缓存
  - 减少 DB 压力
```

### 10.3 关注关系

```
图数据库（Neo4j / JanusGraph）：
  - 关注 / 被关注关系
  - 多跳查询

Redis：
  - 关注列表缓存
  - 反向关注（粉丝列表）
```

## 11. 性能优化

### 11.1 缓存策略

```
多级缓存：
  - L1：本地缓存（5 分钟）
  - L2：Redis（10 分钟）
  - L3：DB

冷热分离：
  - 热门 Feed：缓存
  - 长尾 Feed：DB
```

### 11.2 预加载

```
用户进入 Feed：
  - 预加载前 5 页
  - 后台预加载后 5 页
  → 翻页流畅
```

### 11.3 分页策略

```
传统分页：OFFSET LIMIT
  - OFFSET 大时性能差
  - 深翻页慢

游标分页：
  - 用 (timestamp, id) 作为游标
  - WHERE timestamp < cursor LIMIT N
  - 性能稳定
```

## 12. 经典面试题

### 12.1 朋友圈设计

```
Q：设计朋友圈 Feed 流
A：
  - 推模式为主（关注数 < 5000）
  - Redis Sorted Set 收件箱
  - 异步扩散（Kafka）
  - 大 V 走拉模式
  - 关注关系存图数据库

追问：如何保证实时性？
  - 推模式天然实时
  - 拉模式 + 5 分钟缓存

追问：超大 V（1 亿粉丝）怎么处理？
  - 拉模式（不扩散）
  - 读时合并
```

### 12.2 推荐 Feed 设计

```
Q：设计抖音推荐流
A：
  - 纯拉模式（不基于关注）
  - 多路召回 + 精排
  - 实时特征 + 离线特征
  - Redis 缓存结果
  - Flink 实时计算

追问：如何保证不重复？
  - 内容 ID 去重
  - 用户已经看过的内容标记
```

### 12.3 微博设计

```
Q：设计微博 Feed 流
A：
  - 混合模式（推 + 拉）
  - 关注流 + 推荐流双流
  - 关注流推模式（互关）+ 拉模式（大 V）
  - 推荐流算法 + 实时计算
```

## 13. 一句话总结

```
📌 Feed 流核心难题：写入扩散 vs 读取聚合的取舍
📌 推模式：读快写慢，适合中小规模
📌 拉模式：写快读慢，适合大规模
📌 混合模式：按用户类型区分，主流方案
📌 大 V 必须特殊处理（拉模式）
📌 存储：Redis Sorted Set（收件箱）+ MySQL（发件箱）+ 图数据库（关注）
📌 现代 Feed 是混合模式 + 推荐算法 + 实时计算的复杂系统
```
