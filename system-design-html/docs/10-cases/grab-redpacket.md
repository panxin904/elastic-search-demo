# 抢红包系统设计

> 群里发红包，几百人抢。**公平性 + 实时性 + 不超发**。

## 1. 红包的核心难题

```
场景：
  老板发 1000 元红包，50 人抢
  → 每人 20 元平均？
  → 还是随机？

实际：
  - 拆红包金额随机（手气最佳）
  - 总和必须正好 1000
  - 不超发、不漏发
  - 抢到的金额要实时可见

核心约束：
  - 公平性：随机但总和准确
  - 实时性：几万人抢几百个红包，要快
  - 可用性：不能宕机
```

## 2. 红包的两种类型

### 2.1 普通红包（拼手气）

```
发红包：
  - 总额 1000 元
  - 50 个包
  - 每人随机金额
  - 总和 = 1000（精确）

用户抢：
  - 抢到一个金额
  - 实时显示手气最佳
```

### 2.2 等额红包

```
发红包：
  - 总额 1000 元
  - 50 个包
  - 每包 20 元（固定）

用户抢：
  - 抢到 20 元
  - 抢完为止
```

## 3. 拆红包算法

### 3.1 普通红包（随机金额）

```
约束：
  - 总和 = N
  - 份数 = K
  - 每份 ∈ [min, max]
  - 不能出现"最后一份过大"

常见算法：二倍均值法

```python
def split_redpacket(total, count):
    """二倍均值法"""
    min_amount = 0.01
    max_amount = total / count * 2  # 二倍均值
    
    amounts = []
    remaining = total
    
    for i in range(count - 1):
        # 当前份：min 到 二倍均值之间随机
        max_now = min(max_amount, remaining - (count - i - 1) * min_amount)
        amount = random.uniform(min_amount, max_now)
        amount = round(amount, 2)  # 保留 2 位小数
        amounts.append(amount)
        remaining -= amount
    
    amounts.append(round(remaining, 2))  # 最后一份拿剩余
    return amounts
```

特点：
  - 每份期望 = 平均值
  - 不出现极端值
  - 总和精确 = total
```

### 3.2 预生成 vs 实时生成

```
预生成：
  发红包时生成所有金额，写到 Redis List
  用户抢时 LPOP
  优点：原子（Redis 单线程）
  缺点：金额提前泄露

实时生成：
  用户抢时实时算金额
  优点：公平性更好（看不到前面人的金额）
  缺点：需要复杂的分布式计算

📌 工程上多用预生成（Redis List + LPOP）
   - 手气最佳靠客户端展示顺序
```

## 4. 整体架构

```
用户抢红包
    ↓
网关（限流 / 风控）
    ↓
抢红包服务
    ↓
Redis（红包金额队列 + 抢红包记录）
    ↓
MQ
    ↓
红包服务（异步更新 DB）
    ↓
DB（账户余额）
```

## 5. 关键设计

### 5.1 红包预生成（Redis List）

```
发红包时：

  amount_list = split_redpacket(total=1000, count=50)
  redis.del("redpacket:123")  # 清空（如果有）
  redis.rpush("redpacket:123", *amount_list)

  redis.set("redpacket:123:total", 1000)
  redis.set("redpacket:123:creator", user_id)
  redis.set("redpacket:123:created_at", now)

📌 Redis List 存所有金额
   抢红包就是 LPOP 一个金额
```

### 5.2 抢红包（Redis Lua 原子）

```lua
-- KEYS[1]: 红包 list
-- KEYS[2]: 已抢记录 set
-- ARGV[1]: user_id
-- ARGV[2]: 时间戳

local amount = redis.call('LPOP', KEYS[1])
if amount == false then
    return -1  -- 抢完了
end

-- 记录谁抢到了
redis.call('SADD', KEYS[2], ARGV[1])

return tonumber(amount)
```

```
原子性：
  - LPOP + SADD 在 Lua 里原子
  - 不会出现"两个人抢同一个红包"
  - 不会出现"红包金额被重复扣"
```

### 5.3 防重复抢

```
用户重复抢：
  - 用 user_id 做 SADD
  - 抢到的人加入集合
  - 二次抢 → 检查集合

代码：
  if redis.call('SISMEMBER', 'bought:rp_123', user_id) == 1 then
      return -2  -- 已抢过
  end

📌 一人只能抢一次
```

## 6. 余额更新

```
用户抢到金额后：
  1. Redis LPOP 拿到金额
  2. MQ 异步发"用户 + 金额"
  3. 后台 worker 更新 DB 用户余额
  4. 通知用户（手气最佳）

原子性保证：
  - Redis 抢到 = 钱"分配"了
  - DB 更新可能延迟
  → 极端情况：Redis 抢了但 DB 没更新
  → 定时对账修复
```

## 7. 过期与退款

```
红包过期（24h 未抢完）：
  - 定时任务扫描
  - 剩余金额退回发红包人
  - Redis List 长度 > 0 且超时

实现：
  - Redis ZSet 存红包 + 过期时间
  - worker 定期 ZRANGEBYSCORE 找过期红包
  - LLEN > 0 → 退款
```

## 8. 公平性问题

### 8.1 手气最佳公平性

```
问题：
  - 抢得早的人运气更好？
  - 抢得晚的人更容易拿大额？

工程上：
  - 预生成 + 随机：金额顺序是固定的
  - 用户感知到的"公平"靠运气
  - 没有真正的"先抢占便宜"

📌 不要纠结"完美公平"
   红包是娱乐，不是金融
```

### 8.2 机器抢红包

```
机器人：
  - 抢得快（毫秒级）
  - 抢得准（指定金额范围）
  - 模拟多个账号

风控：
  - 抢红包频率限制
  - 滑块 / 验证码
  - 行为分析

📌 抢红包的风控比秒杀更严
   因为金额确定，可针对
```

## 9. 高并发优化

### 9.1 Redis 预分片

```
单 Redis 实例扛不住：
  - 红包按 group_id / creator_id 分片
  - 不同红包在不同 Redis 实例
  - 抢红包并发分散到多 Redis

优点：
  - 线性扩展
  - 单 Redis 压力小
```

### 9.2 红包预生成 + 内存缓存

```
热点红包（如明星发红包）：
  - 发红包时预生成所有金额
  - 金额放到内存缓存（不用每次查 Redis）
  - 抢完一批再加载下一批

适合：
  - 极短时间内大量抢
  - 红包金额相对固定
```

### 9.3 异步通知

```
抢到红包后：
  - 立即返回金额给用户
  - 异步发通知（短信 / Push）
  - 不阻塞抢红包流程

MQ：
  - 用户抢到 → 发 MQ 消息
  - worker 异步处理
  - 发 Push + 更新 DB
```

## 10. 经典面试题

### 10.1 拆红包算法

```
Q：怎么保证总和 = 1000 且随机？
A：
  - 二倍均值法：每份期望 = 平均值
  - 最后一份拿剩余（避免浮点误差）
  - 预生成所有金额存 Redis List

追问：为什么不实时算？
  - 实时算需要分布式协调
  - 预生成简单可靠（Redis 单线程）
  
追问：手气最佳怎么算？
  - 客户端拿到金额后显示排名
  - 不依赖服务端计算
```

### 10.2 高并发抢红包

```
Q：1 万 QPS 抢红包怎么设计？
A：
  1. 网关限流（按 group / user）
  2. Redis Lua 原子（不超发）
  3. MQ 异步更新 DB
  4. DB 兜底 + 定时对账

追问：Redis 挂了怎么办？
  - 拒绝所有抢红包请求
  - 或降级为直接读 DB（极慢）
  
追问：抢到但 DB 没更新？
  - 定时对账脚本
  - 用户余额以 DB 为准
```

## 11. 一句话总结

```
📌 红包核心：拆红包算法 + Redis Lua 原子 + MQ 异步 + DB 兜底
📌 二倍均值法：每份期望 = 平均值，随机但总和准确
📌 Redis List 预存金额：LPOP 原子、不超发、不重复抢
📌 SADD 记录已抢：一人一次
📌 过期退款：定时任务扫描过期红包，剩余金额退回
📌 风控：抢红包比秒杀更严（金额确定，机器人更准）
📌 与秒杀的区别：金额确定（不需要预扣），但要公平性
```
