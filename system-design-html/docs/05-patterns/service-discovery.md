# 服务发现

> 微服务架构下，**如何让一个服务找到另一个服务的网络地址**。

## 1. 为什么需要服务发现？

```
单体应用：
  - 服务 A 调用服务 B
  - 直接写死地址：http://192.168.1.100:8080
  - 部署简单，几乎不变

微服务架构：
  - 几十 / 几百个服务
  - 每次发布 IP / 端口都可能变
  - 扩容 / 缩容 / 滚动升级
  - 故障转移
  → 不能写死地址，必须动态发现

📌 核心诉求：
   - 服务注册：服务启动时告诉"我在哪"
   - 服务发现：调用方问"你在哪"
   - 健康检查：剔除挂掉的服务
```

## 2. 两种发现模式

### 2.1 客户端发现（Client-side Discovery）

```
调用流程：
  1. 服务 A 启动 → 注册到 Registry（IP + 端口 + 健康状态）
  2. 服务 A 想调用服务 B
  3. 服务 A 从 Registry 查询 B 的所有实例
  4. 客户端负载均衡（随机 / 轮询 / 一致性哈希）
  5. 直接发请求到 B 的某个实例

┌────────┐         ┌───────────┐         ┌────────┐
│ Service │ ──────► │ Registry  │ ◄────── │Service │
│   A    │  query  │ (服务列表) │  register │  B    │
│        │ ──────► │           │ ──────► │       │
│        │  instance list           │       │
└────────┘         └───────────┘         └────────┘
                      │
                      ▼
                ┌───────────┐
                │  Health   │
                │  Check    │
                └───────────┘

代表：Eureka / Consul（部分模式）/ Kubernetes DNS
```

### 2.2 服务端发现（Server-side Discovery）

```
调用流程：
  1. 服务 A 启动 → 注册到 Registry
  2. 服务 A 调用 B：发给 Load Balancer
  3. Load Balancer 查询 Registry 拿 B 的实例
  4. Load Balancer 转发到 B

┌────────┐      ┌────────────┐      ┌──────────┐      ┌────────┐
│Service │ ───► │ Load       │ ───► │ Registry │ ◄─── │Service │
│   A    │      │ Balancer   │      │          │      │  B    │
│        │      │ (LB)       │      └──────────┘      │       │
└────────┘      └────────────┘                         └────────┘

代表：AWS ELB / GCP Load Balancer / Kubernetes Service
```

### 2.3 对比

```
┌──────────────────┬──────────────────┬──────────────────┐
│                  │ 客户端发现       │ 服务端发现       │
├──────────────────┼──────────────────┼──────────────────┤
│ 负载均衡位置     │ 客户端           │ LB / Sidecar     │
│ 客户端复杂度     │ 高（要集成 SDK）│ 低（透明）       │
│ LB 依赖          │ 无              │ 需要             │
│ 跨语言           │ 难（每语言 SDK） │ 易（HTTP）       │
│ 健康检查         │ 客户端           │ LB              │
│ 代表             │ Eureka / Nacos  │ K8s / ELB       │
└──────────────────┴──────────────────┴──────────────────┘

📌 趋势：客户端发现更灵活，但服务端发现运维更简单
```

## 3. 注册中心选型

### 3.1 主流方案

| 方案 | 类型 | 协议 | 特点 |
|---|---|---|---|
| **Consul** | 客户端 | HTTP/DNS | 健康检查强，多数据中心 |
| **etcd** | 客户端 | HTTP/gRPC | 强一致（Raft），K8s 默认 |
| **Eureka** | 客户端 | HTTP | Netflix 开源，AP 优先 |
| **Nacos** | 双模式 | HTTP/DNS | 阿里开源，配置中心 + 服务发现 |
| **ZooKeeper** | 客户端 | TCP | 强一致，老牌但运维重 |
| **K8s Service** | 服务端 | DNS | K8s 内置，生态完整 |

### 3.2 CAP 取舍

```
etcd / ZooKeeper：CP
  - 强一致
  - 分区时拒绝写入
  - 适合配置、Leader 选举

Eureka：AP
  - 高可用
  - 分区时各节点独立服务
  - 服务发现场景更合适

Nacos：可配置（默认 AP）

📌 服务发现通常更看重可用性（AP）
   因为：
   - 即使注册信息短暂不一致
   - 客户端重试或下次刷新就能恢复
   - 比"注册中心挂了导致所有服务不能发现"好
```

## 4. 健康检查

### 4.1 为什么需要？

```
服务可能：
  - 进程在但 RPC 不通（死锁）
  - 进程在但数据库连不上
  - 进程在但 GC 暂停

光靠心跳不够，需要**应用层探活**
```

### 4.2 两种健康检查

```
被动检查（被动）：
  - 注册中心定期 ping 服务实例
  - 失败超过阈值 → 剔除

主动检查（主动）：
  - 服务实例定期上报心跳
  - 超时未上报 → 剔除

组合：
  - 注册中心 ping + 实例心跳
  → 双重保险
```

### 4.3 健康检查的级别

```
L1：进程存活
  - 进程是否在运行
  - 简单 ping

L2：RPC 可达
  - 能响应 RPC 请求
  - /health 端点返回 200

L3：应用就绪
  - 依赖服务都连上了
  - 数据库 / 缓存 / MQ 都 OK
  - 可对外提供服务

📌 三级都要有，但发布 / 缩容用不同级别
   - K8s liveness probe = L1（是否重启）
   - K8s readiness probe = L3（是否接流量）
```

## 5. 注册中心的高可用

```
注册中心自己也要高可用：
  - etcd / Consul：Raft 多数派（3/5/7 节点）
  - Eureka：AP，多节点独立（最终一致）

注册中心挂了的应对：
  - 客户端缓存服务列表
  - 启动时拉全量 + 定期拉增量
  - 注册中心恢复后重新同步

📌 设计原则：客户端不能依赖注册中心永远可用
```

## 6. 实践案例：微服务集成

### 6.1 Spring Cloud 体系

```
注册中心：Eureka / Consul / Nacos
负载均衡：Ribbon（客户端）/ Spring Cloud LoadBalancer
调用：Feign / OpenFeign
熔断：Hystrix / Sentinel / Resilience4j
网关：Spring Cloud Gateway / Zuul
配置：Spring Cloud Config / Nacos Config

📌 一站式全家桶，但耦合严重
   现代项目倾向：每个组件独立选型
```

### 6.2 K8s 原生

```
K8s Service：
  - 通过 DNS / ClusterIP 暴露
  - 自动负载均衡（iptables / IPVS）
  - 自动健康检查

K8s Ingress：
  - 7 层 LB
  - HTTPS / 路由 / 限流
  - 对外暴露服务

📌 在 K8s 里通常不需要额外注册中心
   Service + DNS 已经够用
```

## 7. 常见陷阱

### 7.1 注册信息滞后

```
场景：
  服务 B 实例挂了
  Registry 还没收到心跳超时
  → A 调用 B 失败

缓解：
  - 健康检查频率足够高
  - 客户端重试 + 快速失败
  - 熔断器剔除失败实例
```

### 7.2 脑裂

```
场景：
  Registry A 和 B 网络分区
  A 端的部分服务认为 B 端的服务"已下线"
  B 端的客户端认为 A 端的服务"已下线"
  → 双向剔除

缓解：
  - 选 CP 注册中心
  - 分区期间拒绝决策
  - 应用层重试
```

### 7.3 雪崩

```
场景：
  Registry 重启 / 网络抖动
  大量客户端同时重连
  → Registry 被打爆

缓解：
  - 客户端退避重试
  - Registry 限流
  - 客户端缓存服务列表（不依赖 Registry 实时）
```

## 8. 一句话总结

```
📌 服务发现是微服务的"中枢神经"：注册 + 发现 + 健康检查
📌 两种模式：客户端发现（灵活）vs 服务端发现（运维简单）
📌 CAP 取舍：服务发现偏向 AP（高可用 > 强一致）
📌 健康检查要分层：进程 / RPC / 应用就绪
📌 K8s 生态下 Service + DNS 已经够用，无需额外注册中心
📌 客户端必须缓存服务列表，不能依赖注册中心永远在线
```
