# 配置中心

> 把分散在各服务的配置文件集中管理，运行时动态推送变更。

## 1. 为什么需要配置中心？

```
传统方式：
  - 每个服务有自己的 application.yml
  - 改配置要重启服务
  - 几百个服务 = 几百份配置
  → 运维噩梦

配置中心：
  - 所有配置集中存储
  - 运行时推送变更
  - 服务无需重启
  - 版本管理 + 回滚 + 灰度
```

## 2. 配置分类

```
按变更频率：

1. 静态配置：
   - 数据库 URL
   - 第三方 API Key
   - 日志级别
   - 几乎不变

2. 准动态配置：
   - 限流阈值
   - 开关（feature flag）
   - 路由规则
   - 偶尔变

3. 动态配置：
   - 业务参数（活动开关）
   - 黑名单 / 白名单
   - 算法参数
   - 经常变
```

## 3. 配置中心核心能力

### 3.1 必备能力

```
1. 配置管理：
   - CRUD
   - 版本控制
   - 灰度发布

2. 动态推送：
   - 配置变更实时推送到服务
   - 服务自动热加载（无需重启）

3. 多环境隔离：
   - dev / staging / prod
   - 不同命名空间

4. 权限审计：
   - 谁改了什么
   - 何时改的
   - 可追溯

5. 高可用：
   - 配置中心自身不能成为单点
   - 客户端缓存配置（不依赖中心一直在线）
```

### 3.2 进阶能力

```
6. 灰度发布：
   - 按机器 / 集群 / 用户分批推送
   - 观察无异常再全量

7. 配置加密：
   - 敏感配置（密码 / 密钥）加密存储
   - 运行时解密

8. 配置依赖：
   - 配置之间的引用
   - 配置的继承 / 覆盖
```

## 4. 主流配置中心

| 方案 | 存储 | 一致性 | 特点 |
|---|---|---|---|
| **Spring Cloud Config** | Git | 弱 | 生态完善，需配合 Spring Cloud Bus |
| **Nacos** | MySQL + 缓存 | 强 | 配置 + 注册中心二合一 |
| **Apollo** | MySQL + 缓存 | 强 | 携程开源，灰度发布强 |
| **etcd** | 内置 | 强（CP） | K8s 原生 |
| **Consul KV** | 内置 | 强 | 多数据中心 |
| **ZooKeeper** | 内置 | 强 | 老牌，运维重 |

## 5. 推送模型

### 5.1 轮询（Pull）

```
客户端定期拉取：
  服务 → 配置中心 GET /config
  → 每 30 秒拉一次

优点：
  - 实现简单
  - 不需要长连接

缺点：
  - 实时性差（30 秒延迟）
  - 服务多时拉取压力大
```

### 5.2 长轮询（Long Polling）

```
客户端发请求，配置中心 hold 住：
  服务 → 配置中心 GET /config?version=xxx
  → 配置中心 hold 直到：
     1. 配置变了（返回新配置）
     2. 超时（返回当前配置）

优点：
  - 准实时（秒级）
  - 减少无效请求

缺点：
  - 服务端需要维护连接状态
```

### 5.3 推送（Push / Watch）

```
配置中心主动推送：
  服务启动时建立长连接
  → 配置变更时，服务端推送到客户端

代表：
  - Nacos UDP 推送
  - Apollo 长轮询 + HTTP
  - etcd watch（gRPC stream）
  - ZooKeeper Watch

优点：
  - 实时性好

缺点：
  - 连接管理复杂
  - 断线重连 + 一致性
```

### 5.4 混合方案

```
实际生产：
  - 客户端首次启动：拉全量
  - 定期轮询：兜底（防止推送丢失）
  - 实时推送：变更秒级生效
  - 内存缓存：避免每次访问都查
```

## 6. Apollo 详解（参考实现）

### 6.1 架构

```
┌─────────────────────────────────────────┐
│             Portal (管理后台)            │
│  - 配置 CRUD                             │
│  - 灰度发布                             │
│  - 权限审计                             │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│          Admin Service (管理服务)        │
│  - 配置读写 API                          │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│          Config Service (配置服务)       │
│  - 客户端长轮询                          │
│  - 配置推送                              │
└──────────────┬──────────────────────────┘
               │
               ▼
       ┌───────────────┐
       │  MySQL        │  (持久化)
       └───────────────┘
```

### 6.2 推送流程

```
1. 管理员在 Portal 改配置
2. Portal 调 Admin Service 写 MySQL
3. Admin Service 通知 Config Service
4. Config Service 唤醒长轮询的客户端
5. 客户端收到通知，重新拉取配置
6. 客户端更新内存配置 + 触发监听器
```

### 6.3 灰度发布

```
发布配置时：
  - 选择灰度维度（IP / 集群 / Label）
  - 只推送给灰度范围内的实例
  - 观察无异常后一键全量
  - 有问题可回滚

📌 比简单全量推送安全得多
```

## 7. 配置变更的热加载

### 7.1 三种实现

```
方案 1：监听器
  - 业务代码注册配置变更监听器
  - 配置变了 → 触发回调 → 重新初始化业务对象

方案 2：注解 + AOP
  - @Value("${rate.limit}") 直接注入
  - Spring Cloud 配合 RefreshScope 注解
  - 配置变更 → Bean 重建

方案 3：动态代理
  - 配置对象是动态代理
  - 每次访问读最新值
```

### 7.2 注意事项

```
1. 线程安全：
   配置对象可能被多线程访问
   → 不可变对象 / CopyOnWrite

2. 不一致窗口：
   推送有延迟
   → 灰度发布避免全量不一致

3. 回滚：
   推送错了要能快速回滚
   → 版本历史

4. 配置校验：
   推送前校验（类型 / 范围 / 必填）
   → 避免推错配置让服务不可用
```

## 8. 配置中心的陷阱

### 8.1 配置中心挂了

```
场景：
  配置中心宕机 / 网络分区
  客户端拿不到配置

应对：
  - 客户端必须有本地缓存
  - 启动时拉全量到本地
  - 后续读本地
  - 配置中心恢复后再同步
```

### 8.2 配置漂移

```
场景：
  多个环境（dev/staging/prod）的配置被人工改过
  没有记录，无法追溯

应对：
  - 所有变更走配置中心 Portal
  - 不允许直接改配置文件
  - Git 仓库存档（Spring Cloud Config 模式）
```

### 8.3 配置大爆炸

```
场景：
  几万个配置项
  推送一次全量 = 几万个服务同时 reload

应对：
  - 按 namespace 拆分
  - 按重要程度分批推送
  - 关键配置独立发布
```

## 9. 实战案例

### 9.1 Spring Cloud Config + Git

```
配置存在 Git：
  - 版本控制天然支持
  - 回滚 = git revert
  - 审计 = git log

缺点：
  - 实时性差（需配合 Spring Cloud Bus 推送）
  - 配置中心自身要维护
```

### 9.2 Nacos

```
Nacos = 配置中心 + 注册中心
  - 配置管理 UI
  - 服务发现 UI
  - 数据一致性
  - 集群部署

📌 国内最常用的事实标准
```

### 9.3 K8s ConfigMap + Secret

```
K8s 模式：
  - ConfigMap 存普通配置
  - Secret 存敏感配置
  - 通过 Volume 挂载到 Pod
  - 配置变更自动通知（inotify）

优势：
  - 与 K8s 生态整合
  - 配置和部署绑定

限制：
  - 不适合频繁变更
  - 推送延迟相对较高
```

## 10. 一句话总结

```
📌 配置中心解决"配置分散 + 改配置要重启"两大痛点
📌 三类配置：静态 / 准动态 / 动态
📌 推送模型：轮询 / 长轮询 / Watch，混合方案最稳
📌 客户端必须本地缓存，不能依赖配置中心永远可用
📌 灰度发布是配置中心的杀手锏（Apollo 强项）
📌 国内首选 Nacos，K8s 生态用 ConfigMap + Secret
📌 业务侧要监听配置变更做热加载，避免重启
```
