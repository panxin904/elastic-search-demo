# 熔断器模式

> Martin Fowler 2014 年提出。当下游服务故障时，**快速失败**而不是傻等。

## 1. 没有熔断器会怎样？

```
场景：服务 A → 服务 B

服务 B 故障（慢 / 挂）：
  - A 发请求到 B
  - B 不响应（或响应很慢）
  - A 的线程池被 B 的请求占满
  - A 也跟着挂
  - 雪崩：A 挂了 → A 的上游 C 也跟着挂
  → 一个服务故障，全链路崩溃

📌 这就是"雪崩效应"
```

## 2. 熔断器的三种状态

```
        失败超过阈值
  ┌──────────────────────► ┌──────────┐
  │                        │  OPEN    │（熔断打开）
  │                        │  拒绝    │
  │                        └─────┬────┘
  │                              │ 超时窗口到期
  │                              ▼
  │                        ┌──────────┐
  │                        │HALF_OPEN │（半开）
  │                        │ 试探请求 │
  │                        └─────┬────┘
  │                              │ 试探成功
  │       试探失败               │
  └──────────────────────┐      │
                           │      ▼
                       ┌──────────┐
                       │ CLOSED   │（熔断关闭）
                       │ 正常调用 │
                       └──────────┘

CLOSE：正常调用所有请求
OPEN ：快速失败（不调下游）
HALF：放少量请求试探，成功 → CLOSE，失败 → OPEN
```

## 3. 状态机详解

### 3.1 CLOSED（关闭）

```
正常状态：
  - 所有请求都调用下游
  - 统计错误率
  - 错误率超过阈值 → OPEN

统计窗口：
  - 滑动窗口（最近 N 次请求）
  - 或最近 N 秒请求

阈值：
  - 错误率 > 50%（举例）
  - 慢调用率 > 60%
  - 配置项，可调
```

### 3.2 OPEN（打开）

```
熔断状态：
  - 快速失败：直接抛异常，不调下游
  - 不消耗线程
  - 持续一段时间（sleep window）→ HALF_OPEN

快速失败的响应：
  - 抛 CircuitBreakerOpenException
  - 返回 fallback（兜底数据 / 默认值 / 缓存）
  - 记录指标
```

### 3.3 HALF_OPEN（半开）

```
试探状态：
  - 放行少量请求（N 个）
  - 统计这些请求的成功率
  - 成功率 > 阈值 → CLOSED（恢复正常）
  - 成功率 < 阈值 → OPEN（继续熔断）

试探数量：5-10 个
阈值：70-80% 成功率
```

## 4. 关键参数

```
1. 滑动窗口大小：
   - 10s / 100 次请求
   - 太小易误判，太大反应迟钝

2. 错误率阈值：
   - 50% 是常用起点
   - 业务可根据 SLO 调整

3. sleep window：
   - 熔断持续时间（10s-60s）
   - 太短易抖动，太长恢复慢

4. 试探请求数：
   - 5-10 个
   - 太少不准确，太多风险大

5. 半开阈值：
   - 试探成功率要求
   - 70-80%

📌 所有参数都应该可配置、可监控
   实际生产中需要根据业务调优
```

## 5. Fallback（兜底）

```
熔断后不是直接抛异常，而是：
  1. 返回默认值
     - 列表查询 → 返回空列表
     - 配置查询 → 返回本地缓存

  2. 返回降级数据
     - 推荐服务挂了 → 返回热门商品
     - 评论服务挂了 → 不显示评论

  3. 走本地逻辑
     - 远程调用 → 查本地缓存
     - 同步调用 → 异步队列

  4. 抛业务异常
     - 让上层处理
     - 返回友好的错误提示

📌 没有 fallback 的熔断 = 把故障换了个地方
```

## 6. 主流实现

### 6.1 Hystrix（Netflix，已停维）

```
历史地位：
  - Java 生态第一个成熟的熔断器
  - 2018 年 Netflix 停止开发
  - 但设计思想被广泛借鉴

特点：
  - 线程隔离（信号量 / 线程池）
  - 熔断器
  - 降级
  - 监控

📌 新项目不建议用，维护已经停止
```

### 6.2 Resilience4j（Hystrix 继任者）

```
Java 生态主流选择：
  - 模块化设计
  - 函数式 API
  - 支持熔断 / 限流 / 重试 / 隔离

模块：
  - resilience4j-circuitbreaker：熔断
  - resilience4j-ratelimiter：限流
  - resilience4j-retry：重试
  - resilience4j-bulkhead：隔离
  - resilience4j-timelimiter：超时
```

### 6.3 Sentinel（阿里）

```
国内最常用：
  - 流量控制 / 熔断降级 / 系统保护
  - 丰富的规则配置
  - 实时监控

特点：
  - 控制台可视化
  - 集群限流
  - 热点参数限流

📌 与 Spring Cloud / Dubbo 集成好
```

### 6.4 其他

```
- Polly（.NET）
- Hystrix-go（Go，已停维）
- sony/gobreaker（Go，简单）
- Istio（服务网格层熔断）
```

## 7. 线程隔离

### 7.1 为什么需要？

```
即使有熔断器，调用下游还是会占用线程：
  - 下游慢 → 线程被占 → 上游线程池耗尽

线程隔离：
  - 给每个下游一个独立的线程池
  - 下游慢只影响自己线程池
  - 不影响其他下游

两种隔离：
  - 信号量隔离：不换线程，轻量
  - 线程池隔离：换线程，重但隔离强
```

### 7.2 实际选择

```
默认用信号量隔离（性能好）：
  - 并发数限制
  - 不切线程

线程池隔离用于：
  - 调用链很长
  - 需要超时控制严格
  - 不在乎性能损失

📌 Sentinel 默认信号量隔离
   Hystrix 默认线程池隔离（已过时）
```

## 8. 熔断器组合

```
熔断 + 重试：

  熔断器 CLOSED 状态：
    1. 请求失败
    2. 重试（最多 3 次）
    3. 都失败 → 计入错误率
    4. 错误率超阈值 → 熔断

📌 注意：
   - 重试会放大请求量
   - 只对幂等操作重试
   - 熔断后再重试无意义
```

## 9. 监控指标

```
必须监控的指标：
  1. 熔断器状态变化（CLOSED/OPEN/HALF_OPEN）
  2. 熔断次数 / 时长
  3. fallback 调用次数
  4. 错误率 / 慢调用率

📌 熔断器状态变化要告警
   - 频繁熔断 = 下游有问题
   - 长期熔断 = 配置错了
```

## 10. 工程实践

### 10.1 配置原则

```
按下游分级：
  - 关键下游（订单 / 支付）：阈值低（30%），熔断激进
  - 次要下游（评论 / 推荐）：阈值高（70%），熔断保守

按业务分级：
  - 核心链路：兜底数据必须有
  - 非核心链路：直接快速失败
```

### 10.2 实战陷阱

```
陷阱 1：熔断配置过激
  - 误判导致熔断频繁
  - 解决：调高阈值 / 调大窗口

陷阱 2：fallback 不合理
  - 兜底数据导致业务错误
  - 例：库存查询兜底返回 0 → 超卖

陷阱 3：熔断器没有监控
  - 熔断了没人知道
  - 恢复滞后

陷阱 4：熔断粒度太粗
  - 一个服务共用一个熔断器
  - 例：所有接口都受影响

📌 最佳：每个 RPC 调用（service+method）一个熔断器
```

## 11. 一句话总结

```
📌 熔断器是"分布式系统安全气囊"：防止雪崩
📌 三态机：CLOSED（正常）/ OPEN（熔断）/ HALF_OPEN（试探）
📌 关键参数：窗口大小 / 错误率阈值 / sleep 时长 / 试探数
📌 必须配合 fallback：没有 fallback 的熔断 = 故障换地方
📌 Java 主流：Resilience4j（轻量）+ Sentinel（阿里，功能丰富）
📌 熔断粒度要细（按 RPC 调用），配置要分级（关键 vs 次要下游）
📌 监控熔断状态变化，及时发现下游问题
```
