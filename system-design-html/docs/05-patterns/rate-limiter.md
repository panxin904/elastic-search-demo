# 限流

> 保护系统不被突发流量冲垮。**有损服务优于系统崩溃**。

## 1. 为什么需要限流？

```
没有限流的灾难：
  - 突发流量（秒杀 / 热点事件 / 恶意攻击）
  - 服务被冲垮
  - 数据库连接耗尽
  - 全站 500

有限流的保护：
  - 超出阈值的请求：快速失败
  - 服务保护核心用户
  - 业务降级而非系统崩溃
```

## 2. 限流的层次

```
1. 接入层限流（CDN / SLB）：
   - 防御 DDoS
   - 抗 CC 攻击
   - 粗粒度（按 IP / URL）

2. 网关层限流：
   - 全局限流
   - 按用户 / 全局 QPS
   - 中粒度

3. 服务层限流：
   - 单个服务的保护
   - 按业务维度
   - 细粒度

4. 数据层限流：
   - 数据库连接池限流
   - Redis 连接池限流

📌 多层限流组合，纵深防御
```

## 3. 限流算法

### 3.1 固定窗口计数器

```
实现：
  - 维护一个计数器
  - 每秒清零 + 计数
  - 超阈值则拒绝

例：每秒 1000 QPS
  00:00:00 计数器 = 0
  00:00:01 计数器 +1 (1)
  ...
  00:00:01.999 计数器 +1 (1000) → 拒绝
  00:00:02 计数器 = 0

优点：实现极简
缺点：窗口边界问题（双倍突发）
  例：00:00:01.999 来 1000 请求，00:00:02.001 又来 1000 请求
  → 2ms 内处理 2000 请求 = 双倍阈值
```

### 3.2 滑动窗口

```
滑动窗口计数器：
  - 窗口划分为多个小窗口
  - 例：1s 窗口，分 10 个 100ms 子窗口
  - 当前窗口计数 = 所有子窗口之和
  - 滑动前进

优点：解决边界问题
缺点：内存稍多（多个子窗口）
```

### 3.3 漏桶（Leaky Bucket）

```
原理：
  - 请求进入桶
  - 桶以固定速率漏水（即处理请求）
  - 桶满则拒绝

  ┌──────────┐
  │  请求进入  │
  │    ▼    │
  │ ┌──────┐ │
  │ │ 桶    │─┤──► 处理（恒定速率）
  │ └──────┘ │
  └──────────┘

特点：
  - 请求处理速率恒定（削峰填谷）
  - 输出速率稳定
  - 适合"削峰"场景

实现：队列 + 定时任务
```

### 3.4 令牌桶（Token Bucket）

```
原理：
  - 桶里按固定速率放令牌
  - 请求消耗一个令牌
  - 桶空则拒绝

  ┌──────────┐
  │ 令牌生成  │
  │   ▼    │
  │ ┌──────┐ │
  │ │ 令牌  │─┤──► 请求消耗令牌
  │ │  桶   │ │
  │ └──────┘ │
  └──────────┘

特点：
  - 允许突发（桶满时可以拿走所有令牌）
  - 平均速率受限
  - 既能削峰也能允许波动
  - 最常用的限流算法

实现：定时放令牌 + 计数
```

### 3.5 算法对比

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│              │ 固定窗口     │ 漏桶         │ 令牌桶       │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 削峰         │ 弱           │ 强           │ 中           │
│ 允许突发     │ 否           │ 否           │ 是           │
│ 输出平稳     │ 否           │ 是           │ 否           │
│ 实现复杂度   │ 极低         │ 中           │ 中           │
│ 适用         │ 简单场景     │ 流量整形     │ API 限流     │
│ 代表         │ Nginx        │ -            │ Guava/Sentinel│
└──────────────┴──────────────┴──────────────┴──────────────┘
```

## 4. 限流维度

### 4.1 常见维度

```
1. 全局 QPS：
   - 整个服务总 QPS
   - 例：每秒 10000

2. 单用户 QPS：
   - 每个用户独立限流
   - 例：每个用户每秒 10 次

3. 单 IP QPS：
   - 按 IP 限流
   - 防恶意爬虫

4. 单接口 QPS：
   - 不同接口不同阈值
   - 例：下单接口严限，查询接口宽限

5. 业务参数：
   - 按商品 ID 限流（热点商品）
   - 按用户等级限流（VIP 不限）
```

### 4.2 组合限流

```
例：
  全局 QPS 10000
  AND 单用户 QPS 10
  AND 单 IP QPS 100

任一超限 → 拒绝

实现：
  - 每个维度独立计数器
  - 全部通过才放行
```

## 5. 分布式限流

### 5.1 单机限流的局限

```
单机限流：
  - 计数器在单个进程内
  - N 个实例 → N 倍限流
  - 例：每实例 100 QPS × 10 实例 = 1000 QPS
  → 集群总限流不准确

需要：分布式限流
```

### 5.2 Redis 分布式限流

```
方案 1：INCR + EXPIRE
  - 用 INCR 计数
  - 第一次 INCR 时设 EXPIRE
  - 超阈值则拒绝

方案 2：Lua 脚本原子
  - INCR + EXPIRE 原子
  - 避免边界问题

方案 3：滑动窗口（Lua）
  - ZADD 时间戳到 ZSet
  - ZREMRANGEBYSCORE 移除过期
  - ZCARD 计数

📌 限流不是严格计费
   Redis 限流允许少量误差
```

### 5.3 Sentinel 集群限流

```
Sentinel 集群流控：
  - Token Server 统一分配令牌
  - 各节点从 Token Server 拿令牌
  - 适合极精确的集群限流

适用：
  - 全集群总 QPS 必须精准
  - 单 Redis 不够用
```

## 6. 限流后的处理

### 6.1 拒绝策略

```
1. 直接拒绝：
   - 返回 429 Too Many Requests
   - 客户端处理

2. 排队等待：
   - 同步等待一段时间
   - 不适合高并发（线程占用）

3. 降级：
   - 返回默认值
   - 返回兜底数据
   - 异步处理（写队列）
```

### 6.2 客户端处理

```
被限流后（429）：
  - 退避重试（指数退避）
  - 显示"系统繁忙，请稍后再试"
  - 排队提示
  - 缓存当前请求

📌 退避算法：
  重试间隔 = min(基础间隔 × 2^次数, 最大间隔) + 随机抖动
```

## 7. 热点限流

```
场景：
  秒杀爆款，1 万 QPS 都打一个商品 ID
  → 商品查询服务压力巨大

热点限流：
  - 探测热点参数（如商品 ID）
  - 单独限流热点参数
  - 非热点参数正常限流

Sentinel 实现：
  - 热点参数限流
  - 例：param "productId" 单独限流
```

## 8. 限流 vs 熔断 vs 降级

```
┌──────────┬─────────────────────────────────────────────┐
│ 限流     │ 主动：保护系统，按规则拒绝超阈值的请求        │
├──────────┼─────────────────────────────────────────────┤
│ 熔断     │ 被动：下游故障时，快速失败防止雪崩            │
├──────────┼─────────────────────────────────────────────┤
│ 降级     │ 主动 / 被动：牺牲非核心功能，保核心功能        │
└──────────┴─────────────────────────────────────────────┘

三者配合：
  - 限流在入口（防流量）
  - 熔断在调用链（防雪崩）
  - 降级在结果（保核心）

📌 三者一起用 = 高可用三大支柱
```

## 10. 工程实践

### 10.1 限流配置

```
按接口分级：
  - 支付：100 QPS（严）
  - 下单：500 QPS
  - 查询：5000 QPS（宽）

按用户分级：
  - 普通用户：10 QPS
  - VIP：100 QPS
  - 内部账号：无限制

按优先级：
  - 核心链路：宽松
  - 非核心链路：严格
```

### 10.2 限流监控

```
必须监控：
  1. 实时 QPS（与阈值对比）
  2. 拒绝率
  3. 限流分布（哪个接口被限最多）

告警：
  - 拒绝率 > X% → 告警
  - 持续接近阈值 → 提前扩容
```

### 10.3 常见陷阱

```
陷阱 1：限流值拍脑袋
  - 凭经验设限流值
  - 没有压测数据支撑

陷阱 2：限流配置分散
  - 每个服务自己限流
  - 全局不统一

陷阱 3：被限流后体验差
  - 直接 500
  - 应该有友好提示

陷阱 4：限流值长期不调
  - 业务增长但限流值不变
  - 需要定期 review
```

## 11. 一句话总结

```
📌 限流是"有损服务优于系统崩溃"的兜底
📌 主流算法：令牌桶（最常用）/ 漏桶 / 滑动窗口
📌 限流维度：全局 / 用户 / IP / 接口 / 业务参数
📌 分布式限流靠 Redis Lua 或 Sentinel 集群
📌 限流 + 熔断 + 降级 = 高可用三大支柱
📌 配置要分级（按接口 / 按用户），监控要实时
📌 被限流后必须有兜底（直接 500 = 把问题丢给客户端）
```
