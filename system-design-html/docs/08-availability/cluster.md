# 集群模式

> 多节点共同提供同一服务，任何一个挂了不影响整体。**水平扩展、故障转移、负载均衡**。

## 1. 什么是集群？

```
集群（Cluster）：
  - 多台机器共同提供 1 个服务
  - 对外是 1 个整体
  - 单机故障不影响服务

集群 vs 主从：
  - 主从：有明确主从角色，写只走主
  - 集群：所有节点对等，共同提供服务

集群 vs 分布式：
  - 集群：多机做同一件事
  - 分布式：多机做不同的事，协作完成业务
```

## 2. 集群模式分类

### 2.1 主备集群

```
        Master
          │
    ┌─────┼─────┐
    ↓     ↓     ↓
  Standby1 Standby2 Standby3

特点：
  - 只有 Master 提供服务
  - Standby 平时不服务（部分方案可读）
  - Master 挂了，从 Standby 选 1 个
```

### 2.2 对等集群（Peer-to-Peer）

```
  Node1 ←→ Node2
    ↑         ↑
    ↓         ↓
  Node3 ←→ Node4

特点：
  - 所有节点对等
  - 共同分担读写
  - 任何一个挂不影响
  - Cassandra / Riak / Consul
```

### 2.3 分片集群（Sharding）

```
  Shard1     Shard2     Shard3
  (3副本)    (3副本)    (3副本)
  ┌────┐    ┌────┐    ┌────┐
  │M-FS│    │M-FS│    │M-FS│
  └────┘    └────┘    └────┘
  M=Master, F=Follower, S=Secondary

特点：
  - 数据分片，每个 shard 多副本
  - 总容量 = shard 数 × 节点数
  - MongoDB / ES / Kafka / Cassandra
```

## 3. 集群的核心能力

### 3.1 故障转移（Failover）

```
检测：
  - 心跳（每 1-3s）
  - 3 次超时 → 标记为失败

转移：
  - 主从集群：从 Standby 选 1 个
  - 对等集群：调整成员列表
  - 分片集群：副本接管

📌 转移时间：
   10-30s（典型）
   关键业务需要更短（< 5s）
```

### 3.2 水平扩展（Scale Out）

```
加节点：
  - 启动新节点
  - 加入集群（自动发现）
  - 数据再平衡（Rebalance）

加节点的影响：
  - 对等集群：自动 rebalance
  - 分片集群：rebalance 某个 shard
  - 主从集群：变成 Slave / 新建 shard

📌 水平扩展 vs 垂直扩展：
   水平：加机器（云时代首选）
   垂直：升级单机（有限）
```

### 3.3 负载均衡

```
请求分发：
  - L4 负载均衡（Nginx / HAProxy / LVS）
  - L7 负载均衡（API Gateway / Envoy）
  - 客户端负载均衡（gRPC pick_first）

健康检查：
  - 健康节点才接受请求
  - 失败节点自动剔除
  - 恢复后自动加入
```

### 3.4 数据一致性

```
强一致（CP）：
  - ZooKeeper / etcd
  - Paxos / Raft
  - 牺牲可用性

最终一致（AP）：
  - Cassandra / Riak
  - 异步复制
  - 牺牲一致性

📌 多数集群是最终一致
   强一致集群性能差
```

## 4. 典型集群方案

### 4.1 ZooKeeper 集群

```
架构：
  ┌────┐  ┌────┐  ┌────┐
  │ ZK1│  │ ZK2│  │ ZK3│
  └─┬──┘  └─┬──┘  └─┬──┘
    └────────┼────────┘
            ↓
          Client

特点：
  - 3 或 5 节点（奇数）
  - ZAB 协议
  - 强一致
  - 半数存活即可服务
  - Leader 选举

📌 适合：配置中心 / 命名服务 / 分布式锁
   不适合：海量数据存储
```

### 4.2 Redis Cluster

```
架构：
  ┌────────┐  ┌────────┐  ┌────────┐
  │Master1 │  │Master2 │  │Master3 │
  │Slot0-5 │  │Slot6-10│  │Slot11-15│
  └───┬────┘  └───┬────┘  └───┬────┘
      │           │           │
   ┌──┴──┐     ┌──┴──┐     ┌──┴──┐
   │S1   │     │S2   │     │S3   │
   └─────┘     └─────┘     └─────┘

特点：
  - 16384 槽分片
  - 每 Master 1+ Slave
  - 客户端路由（CRC16 slot）
  - 自动故障转移
  - 异步复制（最终一致）
```

### 4.3 Kafka 集群

```
架构：
  ┌─────────┐
  │Controller│ （KRaft 模式：3 节点 raft）
  └─────────┘
       ↓
  ┌────┐  ┌────┐  ┌────┐
  │B1  │  │B2  │  │B3  │  Brokers
  └──┬─┘  └──┬─┘  └──┬─┘
     P0      P1      P2     Partitions
     ├─R1    ├─R1    ├─R1   Replicas
     └─R2    └─R2    └─R2

特点：
  - Partition 分片
  - 每个 Partition 多副本
  - Controller 管理（KRaft 模式基于 Raft）
  - ISR 机制（in-sync replicas）
  - 强一致（acks=all）
```

### 4.4 Elasticsearch 集群

```
架构：
  ┌─────┐  ┌─────┐  ┌─────┐
  │M    │  │M    │  │M    │   Master 节点
  └─────┘  └─────┘  └─────┘
  ┌─────┐  ┌─────┐  ┌─────┐
  │D1   │  │D2   │  │D3   │   Data 节点
  │(P0-1)│  │(P2-3)│  │(P4-5)│
  └─────┘  └─────┘  └─────┘
  ┌─────┐  ┌─────┐
  │C1   │  │C2   │           Coordinating 节点
  └─────┘  └─────┘

特点：
  - Master 节点：管理集群状态
  - Data 节点：存数据
  - Coordinating：路由请求
  - 分片 + 副本
  - 最终一致（默认 1s refresh）
```

### 4.5 MongoDB 分片集群

```
架构：
  ┌────────────────┐
  │  Config Server │   （3 节点，存元数据）
  │  (副本集)       │
  └────────┬───────┘
           ↓
  ┌────────────────┐
  │  mongos        │   （路由）
  │  (无状态)      │
  └────────┬───────┘
           ↓
  ┌────┐  ┌────┐  ┌────┐
  │S1  │  │S2  │  │S3  │   Shard（副本集）
  │(副本)│  │(副本)│  │(副本)│
  └────┘  └────┘  └────┘

特点：
  - Config Server：元数据（3 节点）
  - mongos：路由（可水平扩展）
  - Shard：分片（每个是副本集）
  - Chunk 迁移自动 rebalance
```

## 5. 集群的关键设计

### 5.1 数据分片

```
分片策略：
  1. 哈希分片：key → hash → 模 N
  2. 范围分片：key 范围 → shard
  3. 一致性哈希：hash 环上加节点
  4. 业务分片：按业务主键

📌 选型：
   均匀分布 → 哈希
   范围查询 → 范围
   扩展频繁 → 一致性哈希
```

### 5.2 副本机制

```
副本数：
  - 2 副本：1 挂 = 不可写
  - 3 副本：1 挂 = 仍可写（推荐）
  - 5 副本：2 挂 = 仍可写

副本策略：
  - 主从：1 主多从，写主
  - 主主：多主可写（冲突处理）
  - 无主：所有节点对等（Cassandra）
```

### 5.3 脑裂防护

```
问题：
  - 网络分区
  - 两个子集各自选 Master
  - 双写冲突

解决：
  1. Quorum：必须多数派
  2. Fencing：旧 Master 强制下线
  3. Lease：Master 租约超时自动让位
  4. Witness：第三方仲裁（奇数节点 + 见证节点）
```

### 5.4 集群监控

```
核心指标：
  - 节点存活
  - 副本同步状态
  - 分片均衡度
  - 集群状态变更
  - 慢查询

工具：
  - Prometheus + Grafana
  - Zabbix
  - 集群自带 dashboard（ES / Kafka）
```

## 6. 集群容量规划

```
公式：
  总容量 = 节点数 × 单机容量
  写入 QPS = 节点数 × 单机写 QPS
  读取 QPS = 节点数 × 单机读 QPS × 副本数

冗余：
  - 至少 1 副本冗余
  - 推荐 2 副本（容忍 1 挂）
  - 关键业务 3 副本

📌 1 主 1 备：
   容量 = 1 × 节点容量（备机不服务）

📌 1 主 2 从：
   容量 = 1 × 写容量（主写）
   读容量 = 3 × 读容量
```

## 7. 经典案例

### 7.1 缓存集群

```
场景：电商大促，缓存压力大

方案：Redis Cluster
  - 6 节点（3 Master + 3 Slave）
  - 数据按 key 哈希分片
  - QPS 10万+
  - 节点挂了自动故障转移
```

### 7.2 消息队列集群

```
场景：日均 100 亿消息

方案：Kafka
  - 50 broker
  - 1000 partition
  - 每 partition 3 副本
  - 写入 100万 QPS
```

### 7.3 搜索引擎集群

```
场景：10 亿文档

方案：ES
  - 20 data 节点
  - 100 主分片 + 100 副本
  - 每节点 2TB
  - 查询 P99 < 100ms
```

## 8. 集群设计陷阱

### 8.1 节点数

```
不要 2 节点（脑裂高发）
推荐 3 / 5 / 7 节点
- 3 容忍 1 挂
- 5 容忍 2 挂
- 7 容忍 3 挂

📌 节点越多 = 写入延迟越高（多数派）
   一般 3-5 节点足够
```

### 8.2 数据倾斜

```
问题：
  - 某个 shard 数据量远大于其他
  - 某个节点 QPS 远高于其他

解决：
  1. 选好分片 key
  2. 自动 rebalance
  3. 监控告警
```

### 8.3 级联故障

```
雪崩：
  - 1 节点挂了
  - 其他节点负载升高
  - 全部挂

解决：
  1. 限流（每个节点限流）
  2. 熔断（检测到下游慢就熔断）
  3. 隔离（线程池隔离）
```

## 9. 一句话总结

```
📌 集群 = 多机 + 故障转移 + 水平扩展 + 负载均衡
📌 模式：主备 / 对等 / 分片（最常用）
📌 副本数：3 副本（推荐，容忍 1 挂）
📌 节点数：奇数 3/5/7（脑裂防护）
📌 数据分片：哈希（均匀） / 范围（范围查询） / 一致性哈希（扩展）
📌 典型：ZK 集群（CP）/ Redis Cluster（AP）/ Kafka 集群 / ES 集群
📌 防脑裂：Quorum + Fencing + Lease
📌 容量规划：节点数 × 单机容量 × 副本冗余
```
