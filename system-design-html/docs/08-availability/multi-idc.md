# 多活与单元化

> 多机房同时服务，故障时切流量；按用户分流避免跨机房调用。**异地容灾、就近接入、单元封闭**。

## 1. 为什么需要多活？

```
单机房的问题：
  - 机房断电 / 火灾 / 光纤中断 = 全站不可用
  - 异地用户访问慢
  - 容量有限

多活目标：
  - 高可用：任一机房挂不影响
  - 低延迟：用户就近接入
  - 大容量：水平扩展
```

## 2. 多活模式

### 2.1 同城多活

```
机房 A          机房 B
（上海）         （上海）
 ┌────┐         ┌────┐
 │ 主 │ ←─同步─→│ 备 │
 └──┬─┘         └──┬─┘
    └─────同城────┘
         高速光纤

特点：
  - 同城（< 50km）
  - 延迟 1-3ms
  - 光纤直连
  - 准实时同步
  - 切换时间 30s 内
  - 资源利用率 50%（备机平时不服务）

📌 银行 / 证券 / 强一致业务
```

### 2.2 异地多活

```
机房 A         机房 B         机房 C
（北京）        （上海）        （广州）
 ┌────┐        ┌────┐        ┌────┐
 │ 主 │ ←─异步─→│ 主 │ ←─异步─→│ 主 │
 └──┬─┘        └──┬─┘        └──┬─┘
    └─────异地────┴─────异地────┘
         跨城专线

特点：
  - 跨城（> 500km）
  - 延迟 20-50ms
  - 异步复制
  - 全部提供服务
  - 资源利用率 100%

📌 电商 / 社交 / 互联网业务
```

### 2.3 单元化（Set 化）

```
单元 1                单元 2
┌────────────┐        ┌────────────┐
│ 接入      │        │ 接入      │
│ 业务      │        │ 业务      │
│ 数据      │        │ 数据      │
└────────────┘        └────────────┘
  用户 A-C             用户 D-F

特点：
  - 按用户分单元
  - 单元内全闭环（不跨单元）
  - 单元可独立部署
  - 故障隔离（爆炸半径小）
  - 跨单元调用走服务层

📌 阿里 / 字节 / 美团大规模使用
```

## 3. 多活的关键挑战

### 3.1 数据同步

```
同城：
  - 同步复制（MySQL Group Replication）
  - 准实时（RPO ≈ 0）

异地：
  - 异步复制（binlog 同步）
  - 跨城专线（25-50ms 延迟）
  - RPO = 秒级（可能丢数据）

同步方案：
  1. 数据库同步：MySQL binlog / Oracle GoldenGate
  2. 消息同步：Canal / Debezium + Kafka
  3. 文件同步：rsync / lsyncd
  4. 状态同步：CRDT / OT（协同编辑）
```

### 3.2 数据冲突

```
场景：
  - 机房 A 用户 1 把余额改 100
  - 机房 B 同一用户 1 把余额改 200
  - 同步冲突

解决：
  1. 单元化：按用户路由，单元内不冲突
  2. 互斥写：同一用户只写 1 个机房
  3. 冲突解决：last-write-wins（LWW）/ CRDT
  4. 业务避免：写不冲突的字段
```

### 3.3 全局唯一 ID

```
多活环境的 ID：
  - Snowflake 增加机房 ID bit
  - UUID（无序，DB 不友好）
  - 业务主键 + 机房前缀

要求：
  - 跨机房不重复
  - 大致有序
  - 高可用（不能依赖中心）
```

### 3.4 全局时钟

```
问题：
  - 各机房本地时间不一致
  - 跨机房事件顺序难判定

解决：
  1. NTP 同步（精度 ms）
  2. 原子钟 / GPS（精度 us）
  3. TrueTime API（Google Spanner，精度 ms）
  4. 业务上：避免依赖全局时钟
```

## 4. 流量调度

### 4.1 DNS 调度

```
DNS 智能解析：
  - 用户 DNS 查询
  - DNS 返回最近机房 IP
  - 简单，但有缓存

GSLB（Global Server Load Balancing）：
  - 实时探测机房健康
  - 故障机房自动剔除
  - 调整 DNS 解析权重

📌 DNS 切换慢（5-10 分钟 TTL）
   适合粗粒度调度
```

### 4.2 HTTP 重定向

```
302 重定向：
  - 入口机房返回 302
  - 指向最近机房 URL
  - 精确但多一跳

HTTPDNS：
  - 用 HTTP API 解析 IP
  - 绕过 Local DNS
  - 抗劫持 + 精确调度
```

### 4.3 Anycast IP

```
Anycast：
  - 多个机房共享同一 IP
  - 网络层路由到最近机房
  - BGP 协议
  - DNS 不需要改

📌 CDN 用 Anycast
   1.1.1.1 (Cloudflare) / 8.8.8.8 (Google) 都是 Anycast
```

### 4.4 单元化路由

```
按用户 ID 路由：
  - 用户 1-1000w → 单元 1
  - 用户 1000w-2000w → 单元 2
  - 路由表存在配置中心

实现：
  - 在接入层（API Gateway / Nginx）做
  - 解析用户 ID → 计算单元
  - 转发到对应单元
```

## 5. 单元化架构

### 5.1 典型单元

```
┌──────────────────────────┐
│     单元 (Set)            │
├──────────────────────────┤
│ 接入层  (Nginx/Gateway)   │
│   ↓                      │
│ 业务层  (多个微服务)      │
│   ↓                      │
│ 数据层  (MySQL/Redis)     │
└──────────────────────────┘
  ↓
全局层
  - 中心化数据（账号、商品库）
  - 全局服务（风控、支付）
```

### 5.2 单元化原则

```
原则 1：单元封闭
  - 单元内闭环业务
  - 跨单元调用尽量少
  - 单元可独立部署

原则 2：流量确定
  - 用户 ID 哈希 → 单元
  - 同一用户永远在一个单元
  - 写入也只在一个单元

原则 3：爆炸半径
  - 1 单元挂掉，只影响 1/N 用户
  - 不影响其他单元

原则 4：数据最终一致
  - 单元内强一致
  - 跨单元最终一致
```

### 5.3 路由表

```
配置中心存路由表：
  - 用户 1-1000w → 单元 1
  - 用户 1000w-2000w → 单元 2
  - ...

维度：
  - 用户 ID（账户单元）
  - 商家 ID（商家单元）
  - 地域（地理单元）
  - 业务（业务单元）

更新：
  - 配置变更 → 推送
  - 灰度发布
```

## 6. 多活的部署

### 6.1 阿里多活

```
阿里"三地五中心"：
  - 杭州 + 上海 + 深圳
  - 5 个数据中心
  - 单元化部署
  - 异地多活 + 单元化

切换：
  - 全局控制台
  - 一键切流
  - 切流时间 < 5min
```

### 6.2 美团单元化

```
美团"set 化"：
  - 按用户 ID 哈希分单元
  - 单元内全闭环
  - 跨单元通过中间层
  - 单元容量评估

特点：
  - 单元独立部署
  - 单元独立故障
  - 单元独立扩容
```

### 6.3 字节跳动多活

```
字节"机房对等"：
  - 多个机房对等
  - 流量按地域调度
  - 数据最终一致
  - 强一致业务走中心机房
```

## 7. 多活 vs 容灾

```
多活：
  - 多个机房同时服务
  - 资源利用率 100%
  - 故障时切流量即可

容灾：
  - 备机房平时不服务
  - 主挂了备才接管
  - 资源利用率 50%

📌 多活 = 多机房"全跑" + 切流
   容灾 = 多机房"一跑" + 切换
```

## 8. 经典面试题

### 8.1 设计多活

```
Q：电商多活方案
A：
  1. 3 机房（同城 2 + 异地 1）
  2. 数据按用户 ID 单元化
  3. 单元内闭环（订单/支付/库存）
  4. 跨单元走消息（最终一致）
  5. DNS + HTTPDNS 调度
  6. 数据库双向同步（Canal）
  7. 监控 + 切流平台

追问：数据冲突怎么解决？
  - 单元化：同用户只写 1 单元
  - 不冲突字段：双写 + 后台对账
  - 冲突字段：单点写入 + 跨单元读
```

### 8.2 切流方案

```
Q：机房挂了怎么切？
A：
  1. 监控探测：30s 内确认故障
  2. DNS 摘除：剔除故障机房 IP
  3. API Gateway 重路由：剩余机房
  4. 数据回写：恢复后增量同步
  5. 验证：流量正常 + 数据一致

📌 切流要演练
   真实故障时人慌 = 切错
```

## 9. 何时用多活？

```
✅ 适合：
  - 业务规模大（DAU > 1000w）
  - 容灾要求高（5 个 9）
  - 全球 / 全国分布
  - 投入大（数千万起步）

❌ 不适合：
  - 业务小（单机房足够）
  - 强一致（同城双活）
  - 预算有限
  - 没有跨机房专线

📌 多活是"奢侈品"
   多数业务主备足够
```

## 10. 一句话总结

```
📌 多活 = 多机房同时服务，故障切流
📌 模式：同城双活（强一致） / 异地多活（最终一致） / 单元化（按用户分）
📌 关键技术：流量调度（DNS/HTTPDNS/Anycast） + 数据同步（binlog） + 冲突解决
📌 单元化原则：单元封闭、流量确定、爆炸半径小、最终一致
📌 挑战：数据冲突、全局 ID、全局时钟、跨机房延迟
📌 阿里"三地五中心" / 美团"set 化" / 字节"机房对等"
📌 多活 vs 容灾：全跑 vs 一跑，资源利用率 100% vs 50%
📌 多活是奢侈品，多数业务主备足够
```
