# 容灾演练

> "备胎不用 = 不知道备胎能不能用"。定期演练，确保真故障时能切换。**有备无患，临阵不乱**。

## 1. 什么是容灾？

```
容灾（Disaster Recovery）：
  - 系统遭受灾难时仍能提供服务
  - 灾难：地震、断电、光纤中断、火灾
  - 目标：RTO + RPO 双低

RTO（Recovery Time Objective）：
  - 故障到恢复的时间
  - 目标：1h / 30min / 5min

RPO（Recovery Point Objective）：
  - 故障到丢多少数据
  - 目标：0 / 1min / 1h
```

## 2. 容灾等级

### 2.1 国际标准 SHARE 78

```
Tier 1 - 本地备份
  - 异地磁带备份
  - RTO: 数天
  - RPO: 24h+
  - 成本：低

Tier 2 - 热备
  - 异地机房 + 数据同步
  - RTO: 24h
  - RPO: 几小时
  - 成本：中

Tier 3 - 多活
  - 异地多机房 + 自动切换
  - RTO: 数小时
  - RPO: 分钟级
  - 成本：高

Tier 4 - 双活
  - 双机房同时服务
  - RTO: 分钟级
  - RPO: 秒级
  - 成本：很高

Tier 5 - 双活 + 零丢失
  - 双机房 + 同步复制
  - RTO: 秒级
  - RPO: 0
  - 成本：极高
```

### 2.2 国内分级

```
等保 2.0：
  - 5 级：RTO < 30min, RPO ≈ 0
  - 4 级：RTO < 1h, RPO < 30s
  - 3 级：RTO < 6h, RPO < 5min
  - 2 级：RTO < 24h, RPO < 数小时
  - 1 级：RTO / RPO 无要求

📌 金融行业要求 5 级
   互联网 3-4 级
```

## 3. 容灾架构

### 3.1 同城容灾

```
机房 A          机房 B
 ┌────┐         ┌────┐
 │ 主 │ ←─同步─→│ 备 │
 └────┘         └────┘
  ├─应用
  ├─DB
  └─缓存

故障场景：
  - 主机房断电
  - 备机房接管
  - 切换时间：1-5min

📌 银行 / 证券核心系统
```

### 3.2 异地容灾

```
北京机房       上海机房
 ┌────┐        ┌────┐
 │ 主 │ ←─异步─→│ 备 │
 └────┘        └────┘
  业务中心      异地备份

📌 容忍城市级灾难
   切换时间：30min - 1h
```

### 3.3 两地三中心

```
上海机房 A   上海机房 B   成都机房
   主          同城备       异地灾备
 ┌────┐      ┌────┐      ┌────┐
 │ 主 │ ←─→  │ 备 │ ←─→  │ 灾 │
 └────┘      └────┘      └────┘

📌 国内最常见架构
   同城双活 + 异地灾备
```

## 4. 容灾演练的目的

```
1. 验证架构：
  - 备机真的能起来
  - 数据同步是否完整
  - 切换时间是否达标

2. 验证流程：
  - 切流步骤是否清晰
  - 切流工具是否好用
  - 人员是否熟练

3. 验证业务：
  - 切流后业务是否正常
  - 数据是否一致
  - 用户体验是否可接受

4. 暴露问题：
  - 平时没发现的 bug
  - 文档缺失
  - 监控盲区
```

## 5. 演练类型

### 5.1 桌面演练（Walk-through）

```
内容：
  - 团队会议室推演
  - 不实际切流
  - 讨论每个步骤

时间：
  - 2-4h

频次：
  - 季度 1 次

目的：
  - 熟悉流程
  - 暴露文档问题
```

### 5.2 模拟演练（Simulation）

```
内容：
  - 故障注入（Chaos Engineering）
  - 单系统级别（如关掉 1 个数据库）
  - 不切主流量

工具：
  - Chaos Monkey（Netflix）
  - ChaosBlade（阿里）
  - Litmus（K8s）

时间：
  - 半天

频次：
  - 月度 1 次

目的：
  - 验证单点恢复
  - 培养 oncall 人员
```

### 5.3 实战演练（Full DR）

```
内容：
  - 模拟机房级故障
  - 切真实流量
  - 完整切换流程

风险：
  - 业务可能受影响
  - 必须选低峰期
  - 必须有回滚方案

时间：
  - 周末凌晨

频次：
  - 半年 1 次

目的：
  - 验证真切换
  - 检验 RTO / RPO
```

## 6. 演练流程

### 6.1 演练准备

```
1. 制定方案：
  - 演练目标
  - 演练范围（哪些系统）
  - 演练时间
  - 回滚方案
  - 风险评估

2. 评审方案：
  - 业务方参与
  - 运维 / DBA 评审
  - 安全 / 合规评估

3. 演练资源：
  - 备用环境
  - 监控 dashboard
  - 通信频道（应急群）
  - 故障复现工具

4. 通知：
  - 提前 1 周通知业务方
  - 提前 24h 通知客服
  - 演练前 1h 最后确认
```

### 6.2 演练执行

```
T-0 启动：
  - 应急群通知
  - 各就位
  - 监控开始记录

T+0 注入故障：
  - 关停主服务 / 切网络
  - 记录故障时间

T+30s 监控告警：
  - 监控触发告警
  - oncall 响应
  - 评估是否真故障

T+1min 决策：
  - 决定是否切流
  - 通报指挥

T+2min 切流：
  - DNS 切流 / VIP 漂移
  - 数据库切主
  - 流量监控

T+5min 验证：
  - 业务正常
  - 数据一致
  - 性能正常

T+10min 完成：
  - 业务切回主
  - 验证主恢复
  - 记录切流耗时

T+30min 总结：
  - 关键数据
  - 问题清单
  - 改进建议
```

### 6.3 演练后

```
报告内容：
  - RTO 实测
  - RPO 实测
  - 切流耗时
  - 业务影响
  - 问题清单
  - 改进项

跟进：
  - 问题闭环
  - 自动化改进
  - 下次演练计划
```

## 7. 故障注入工具

### 7.1 ChaosBlade（阿里）

```bash
# 1. CPU 满载
blade create cpu fullload --cpu-count 2

# 2. 内存占用
blade create mem load --mem-percent 80

# 3. 磁盘 IO
blade create disk burn --read --write

# 4. 网络延迟
blade create network delay --time 3000 --interface eth0

# 5. 杀进程
blade create process kill --process tomcat

# 6. 杀容器
blade create docker kill --container-ids <id>
```

### 7.2 Chaos Monkey（Netflix）

```java
// Spring Boot 集成
@ChaosMonkey
public class Application {
    // 自动注入故障
}

// 配置
chaos.monkey.assaults.level=5
chaos.monkey.assaults.latencyActive=true
chaos.monkey.assaults.exceptionsActive=true
chaos.monkey.watcher.repository=true
```

### 7.3 Gremlin

```
商业平台：
  - 跨云支持
  - 可视化
  - 团队协作
  - 合规报告
```

## 8. 常见演练场景

### 8.1 数据库故障

```
演练：
  - Kill 主库
  - 备库自动升级
  - 切流到备库

验证：
  - 业务读写正常
  - 数据无丢失
  - 切换时间 < 30s
```

### 8.2 缓存故障

```
演练：
  - Redis 主节点故障
  - Sentinel 自动切换
  - 客户端重连

验证：
  - 命中率恢复
  - 不影响业务
  - 切换时间 < 5s
```

### 8.3 机房网络中断

```
演练：
  - 模拟机房断网
  - DNS 切流
  - 流量重新分配

验证：
  - 剩余机房能扛住
  - 用户体验可接受
  - 切换时间 < 5min
```

### 8.4 关键服务 OOM

```
演练：
  - 制造 OOM
  - 触发自动重启
  - 验证限流兜底

验证：
  - 服务能恢复
  - 没有级联故障
  - 监控到位
```

## 9. 演练的坑

### 9.1 演练变演戏

```
问题：
  - 演练走过场
  - 切流"假切"（不真实切）
  - 数据造假

解决：
  - 真实切流
  - 第三方监督
  - 真实指标
  - 录像回放
```

### 9.2 演练变事故

```
问题：
  - 演练中真出事故
  - 无法快速回滚
  - 影响业务

解决：
  - 低峰期演练
  - 准备回滚方案
  - 演练隔离（影子流量）
  - 一键回滚
```

### 9.3 没人参与

```
问题：
  - 只有 2 个人演练
  - 其他人不会
  - 真故障时大乱

解决：
  - 全员参与
  - 角色轮换
  - 培训 + 考试
```

## 10. 经典面试题

### 10.1 设计容灾方案

```
Q：电商容灾要求 RTO 5min / RPO 1min
A：
  1. 同城双活（机房 A + 机房 B）
  2. 数据库半同步复制
  3. Redis 双写
  4. DNS + LVS 自动切流
  5. 监控 + 自动告警
  6. 每月演练 1 次

追问：RPO 0 怎么做到？
  - 数据库同步复制
  - Redis 双写
  - MQ 同步刷盘
  - 牺牲性能换强一致
```

### 10.2 演练频次

```
Q：应该多久演练？
A：
  - 桌面演练：季度
  - 模拟演练：月度
  - 实战演练：半年到一年
  - 大版本上线前必演练
```

## 11. 一句话总结

```
📌 容灾 = 备份 + 切换流程 + 演练
📌 关键指标：RTO（恢复时间）+ RPO（数据丢失）
📌 等级：5 级（金融） / 4 级（互联网核心） / 3 级（一般业务）
📌 架构：同城双活 / 异地灾备 / 两地三中心
📌 演练类型：桌面（季度） / 模拟（月度，Chaos Engineering） / 实战（半年）
📌 工具：ChaosBlade（阿里） / Chaos Monkey（Netflix） / Gremlin
📌 演练坑：变演戏、变事故、没人参与
📌 真实切换 + 真实指标 + 录像回放 = 有效演练
```
