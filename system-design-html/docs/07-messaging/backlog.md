# 消息堆积处理

> 消费速度跟不上生产速度，消息堆积是**常态**。关键是**不爆盘**。

## 1. 什么是消息堆积？

```
正常：
  生产速度 = 消费速度
  队列长度 ≈ 0

堆积：
  生产速度 > 消费速度
  队列长度持续增长
  → 延迟增加
  → 可能爆盘（队列满）
```

## 2. 堆积的三大原因

```
1. 突发流量：
   - 大促 / 秒杀
   - 平时 1k TPS → 峰值 100k TPS
   - 消费者扩容来不及

2. 消费者故障：
   - 进程崩溃
   - 慢 SQL / 慢调用
   - 依赖服务故障

3. 业务逻辑变慢：
   - 代码改动
   - 数据量增加
   - 外部 API 变慢
```

## 3. 排查思路

```
步骤 1：看监控
  - consumer lag（堆积量）
  - 消费 TPS
  - 单条消息处理耗时

步骤 2：定位瓶颈
  - 应用层：CPU / 内存 / GC
  - DB 层：慢查询 / 锁等待
  - 依赖：下游服务慢

步骤 3：临时止血
  - 扩容消费者
  - 限流生产者
  - 跳过非关键消息

步骤 4：根本解决
  - 优化消费逻辑
  - 异步化
  - 重新设计架构
```

## 4. 临时方案

### 4.1 扩容消费者

```
紧急扩容：
  - 增加消费者实例
  - 增加 Partition 数（Kafka）
  - 增加 MessageQueue 数（RocketMQ）

注意：
  - Kafka 消费者数 ≤ 分区数
  - 增加分区会影响消息顺序
```

### 4.2 限流生产者

```
源头限流：
  - 上游业务限流（见 rate-limiter.md）
  - 直接拒绝非关键消息
  - 异步转同步（先返回再发消息）

适合：
  - 非实时业务
  - 用户可容忍延迟
```

### 4.3 跳过非关键消息

```
消息分级：
  - P0：必须处理（如支付）
  - P1：重要但不紧急
  - P2：可丢弃

堆积时：
  - P2 消息直接丢弃
  - P1 消息降级
  - P0 消息确保处理

适合：
  - 监控数据（日志 / 指标）
  - 推荐系统（个性化数据）
  - 通知类（短信 / 推送）
```

### 4.4 死信 / 重路由

```
部分消息无法处理：
  - 参数错误 → 永远处理不了
  - 一直重试 → 占用资源

解决：
  - 重试 N 次后进死信队列
  - 人工处理
  - 或重新路由到慢队列
```

## 5. 长期方案

### 5.1 异步化

```
同步处理变异步：

原：
  consumer → DB（同步）
  耗时：100ms/条
  TPS：10

改造：
  consumer → MQ → worker → DB（异步）
  耗时：10ms/条
  TPS：100

📌 异步是提升吞吐的银弹
```

### 5.2 批量处理

```
单条处理变批量：

原：
  for msg in messages:
      process(msg)  # 100ms/条

改造：
  batch = []
  for msg in messages:
      batch.append(msg)
      if len(batch) >= 100:
          process_batch(batch)  # 200ms/100条 = 2ms/条

提升 50x
```

### 5.3 预加载缓存

```
频繁查询 DB：

原：
  process(msg) → query DB → process

优化：
  启动时预加载数据到内存
  process(msg) → 查内存 → 处理

适合：
  - 字典数据
  - 配置
  - 用户基础信息
```

### 5.4 拆分队列

```
所有消息在一个队列：

  - 不能差异化处理
  - 不能独立扩容

拆分：
  - 按业务分（订单 / 支付 / 库存）
  - 按优先级分（关键 / 普通）
  - 按延迟要求分（实时 / 准实时 / 离线）

📌 拆分后单独监控、单独扩容
```

## 6. 消费能力的扩展

### 6.1 Kafka 扩容

```
增加 Partition：
  - 增加 topic 的 partition 数
  - 启动新消费者
  - 自动负载均衡

注意：
  - 已有的消息 key 分区会变（基于新 partition 数）
  - 历史消息可能乱序
  - 增加 partition 是有损操作（生产环境慎用）

最佳实践：
  - 提前预留充足 partition（按未来 3-5 倍预估）
```

### 6.2 RocketMQ 扩容

```
增加 MessageQueue：
  - topic 的 readQueueNums / writeQueueNums
  - 增加消费者实例
  - 自动负载均衡

注意：
  - 顺序消息：扩 queue 数会乱
  - 只能垂直扩展（升级消费者机器）
```

### 6.3 消费者并行度

```
单消费者实例的处理能力：

  process(msg) 单线程：1000 TPS
  process(msg) 多线程：3000 TPS
  process(msg) 协程：10000 TPS

提升方法：
  - 线程池（受限）
  - 协程（Go / Kotlin）
  - 异步 I/O（Netty）
  - 多实例（水平扩展）
```

## 7. 监控与告警

### 7.1 关键指标

```
1. Consumer Lag：
   - 当前未消费消息数
   - 趋势（持续增长 = 堆积）

2. 消费 TPS：
   - 每秒处理消息数
   - 与生产 TPS 对比

3. 处理耗时：
   - P50 / P95 / P99
   - 突增 = 慢查询 / 慢依赖

4. 错误率：
   - 异常 / 重试次数
   - 突增 = 业务故障
```

### 7.2 告警策略

```
告警：
  - lag > 10 万 → 告警
  - lag 持续增长 5 分钟 → 告警
  - 处理耗时 P99 > 1s → 告警
  - 错误率 > 5% → 告警

升级：
  - lag > 100 万 → 严重告警
  - lag 持续 1 小时 → 升级到 P1
  → 值班介入
```

## 8. 实战案例

### 8.1 大促备战

```
618 / 双 11 前：

  1. 预估流量（按去年 3-5 倍）
  2. 提前扩容 partition（不能临阵改）
  3. 压测消费者（找到 TPS 上限）
  4. 准备弹性扩容方案
  5. 准备限流降级开关
  6. 准备应急通道（跳过非关键消息）

📌 消息堆积是"可预期"的，必须提前预案
```

### 8.2 突发流量

```
明星出轨事件 → 微博热搜爆了：

  - 写量突然 100x
  - 评论 / 点赞消息堆积
  - 紧急扩容 + 限流 + 跳过非关键

技术方案：
  - 临时增加 partition
  - 异步化核心路径
  - 监控 + 告警实时升级
```

### 8.3 消费者故障

```
应用 OOM / DB 慢查询：

  - 消费者进程崩溃
  - 消息堆积
  - 重启后继续消费

紧急恢复：
  1. 重启服务（自动恢复）
  2. 慢查询优化（kill long query）
  3. 临时跳过慢消息

📌 关键是快速恢复 + 不丢消息
```

## 9. 一句话总结

```
📌 消息堆积是常态，不是故障，关键是可控
📌 临时方案：扩容 + 限流 + 跳过非关键 + 死信
📌 长期方案：异步化 + 批量处理 + 预加载 + 拆分队列
📌 Kafka 扩容：增加 partition（注意顺序）
📌 监控 lag 趋势比绝对值更重要
📌 大促必须提前预案：分区预留 + 弹性扩容 + 限流降级
📌 不是所有消息都不能丢：日志类可以跳过
```
