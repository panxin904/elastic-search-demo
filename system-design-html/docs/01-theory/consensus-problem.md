# FLP 不可能定理

> Fischer, Lynch, Paterson 1985 年证明：**在异步网络模型下，不存在一个确定性算法能在有限时间内解决共识问题**。

## 1. 共识问题

### 1.1 什么是共识？

```
N 个节点，每个节点初始有一个值 v_i
通过消息传递，最终所有节点**决定**同一个值 v
要求：
  - 一致性（Agreement）：所有诚实节点决定同一个值
  - 有效性（Validity）：决定的值必须是某个节点的初始值
  - 终止性（Termination）：所有诚实节点最终做出决定
```

### 1.2 共识 vs 一致性

```
一致性（Consistency）：读到一致的数据
共识（Consensus）  ：对某个值达成一致决定

共识是更强的原语，常用来实现：
  - Leader 选举（Raft）
  - 分布式锁
  - 原子提交（2PC）
  - 配置变更
```

## 2. FLP 定理陈述

> **在异步网络模型下，即使只有一个进程可能崩溃，也不存在一个确定性算法能保证所有诚实进程最终达成共识。**

拆解：
- **异步网络**：消息可以延迟任意时间，但不能丢失（最终会到）
- **确定性算法**：相同输入产生相同输出
- **单个进程崩溃**：哪怕只有 1 个故障就足够

## 3. 直觉证明

### 3.1 关键观察

```
异步网络的特性：
  - 无法区分"对方慢"和"对方死了"
  - 消息可能无限延迟

如果算法要正确终止：
  - 必须基于已收到的消息做决定
  - 但还有未到的消息可能改变结果
  → 必须等待未知时间
```

### 3.2 构造性证明（思路）

```
假设存在算法 A 在异步网络中总能达成共识
构造一个"敌对调度器"：
  - 让进程的消息延迟无限长
  - 每次算法即将做决定时，延迟关键消息
  - 让进程无法区分"等下一条消息"和"已经决定"

→ 算法永远无法终止 → 矛盾
→ FLP 定理成立
```

### 3.3 工程含义

```
� 不要追求"完美的"分布式共识算法
📌 工程上通过以下方式绕过 FLP：
   1. 引入超时（同步假设）
   2. 随机化（容错性下降但能终止）
   3. 允许最终一致（不要求严格 Termination）
```

## 4. FLP 对工程实践的启示

### 4.1 Raft 如何"绕过" FLP？

```
Raft 不是纯异步系统：
  - 使用超时选举（150-300ms）
  - 假设网络延迟有上界
  → 实际是"部分同步"系统

� Raft 把"消息一定会到"换成"超时后认为对端死了"
   这就是工程对理论的妥协
```

### 4.2 现实中的所有共识算法都"绕过" FLP

| 算法 | 绕过方式 |
|---|---|
| **Paxos** | 超时 + 多数派（部分同步） |
| **Raft** | 超时选举 + 心跳（部分同步） |
| **PBFT** | 视图变更超时（BFT 同步假设） |
| **Bitcoin PoW** | 概率终止（接受小概率分叉） |
| **Tendermint** | 锁机制 + 超时（部分同步） |

## 5. FLP 之外的"不可能"定理

### 5.1 CAP 定理

> 分区期间，A 和 C 只能二选一。

和 FLP 关系：
- CAP 假设**存在分区**（不是异步模型）
- FLP 假设**任意延迟**（异步模型）
- CAP 更宽松 → CAP 内的系统可以解决共识

### 5.2 拜占庭将军问题

> N 个将军中可能有 f 个叛徒，要达成共识至少需要 N ≥ 3f + 1。

FLP 假设是**崩溃故障**（节点死掉或沉默）
拜占庭是**任意故障**（节点说谎、串通）

工程上拜占庭更难：
- 区块链（PoW / PBFT）解决拜占庭
- Raft / Paxos 只解决崩溃故障

## 6. 工程上的"共识"

### 6.1 为什么需要共识？

```
场景 1：分布式锁
  - 多客户端竞争同一资源
  - 必须有一个节点拿到锁
  → 共识决定谁是 Leader

场景 2：配置变更
  - 集群成员变更
  - 所有节点必须知道新成员
  → 共识决定新成员列表

场景 3：原子提交
  - 跨多节点的事务
  - 必须全部成功或全部失败
  → 共识决定 commit / abort

场景 4：Leader 选举
  - 主节点挂了
  - 必须选出新主
  → 共识决定谁是新主
```

### 6.2 共识算法的关键设计

```
1. 多数派（N/2 + 1）：
   - 任意两个多数派必有交集
   - 保证不会出现脑裂

2. 任期 / 轮次：
   - 每次选举增加 epoch
   - 旧 epoch 的决议失效

3. 日志复制：
   - Leader 把日志复制到多数派
   - Follower 按 Leader 的日志覆盖自己

4. 心跳 / 超时：
   - 定期心跳维持 Leader 地位
   - 超时未收到 → 触发选举
```

## 7. 异步模型 vs 同步模型

### 7.1 同步模型

```
假设：消息延迟有上界 D（已知）
  → 算法可以在 2D 内确定对端死了
  → 共识可解
```

### 7.2 异步模型

```
假设：消息延迟任意（无上界）
  → 算法无法区分"慢"和"死"
  → FLP：共识不可解
```

### 7.3 部分同步模型

```
假设：消息延迟有上界，但未知
  → 算法使用超时 + 重试
  → 实际工程的所有共识算法都假设部分同步

Raft / Paxos / PBFT 都属于部分同步
```

## 8. 概率共识（绕过 FLP 的另一条路）

### 8.1 思路

```
不保证"绝对终止"
保证"大概率终止"

Bitcoin PoW：
  - 出块时间 ~10 分钟
  - 6 个块后认为几乎不可逆
  - 但理论上仍可能分叉
  → 概率共识
```

### 8.2 工程取舍

```
概率共识 vs 严格共识：
  概率：吞吐高、终态概率保证
  严格：吞吐低、绝对保证

应用：
  - 金融账务：选严格（Paxos / Raft）
  - 公链：选概率（PoW / PoS）
```

## 9. 一句话总结

```
📌 FLP：异步网络 + 任意延迟 + 单点崩溃 → 共识不可解
📌 工程上所有共识算法都"绕过" FLP：用超时、用概率、用部分同步假设
📌 共识比一致性更强：共识是一致性的基础工具
📌 真正不可解的是"完美"；工程追求的是"足够好"
📌 学习理论的意义不是追求完美，而是知道"为什么不完美"
```
