# 缓存三大问题

> 缓存系统中三类**会打爆数据库**的故障模式，及对应解决方案。

## 1. 三大问题一览

```
┌──────────────┬──────────────────────────────────────────┐
│ 缓存雪崩     │ 大量 key 同时过期 → DB 被打爆           │
├──────────────┼──────────────────────────────────────────┤
│ 缓存穿透     │ 查不存在的 key → DB 反复被打             │
├──────────────┼──────────────────────────────────────────┤
│ 缓存击穿     │ 热点 key 过期瞬间 → DB 被瞬间打爆        │
└──────────────┴──────────────────────────────────────────┘
```

## 2. 缓存雪崩

### 2.1 什么是雪崩？

```
场景：
  大量 key 的过期时间相近（同一批 set）
  过期时间到 → 全部失效
  → 同一时刻所有请求都打到 DB
  → DB 被冲垮

变种：
  - Redis 集群宕机 → 所有请求直接打 DB
  - 重启后大量请求同时打 DB
```

### 2.2 雪崩示意

```
  正常：
    Redis 命中率 90%
       ↓ 10%
    DB QPS = 1 万

  雪崩：
    Redis 命中率 0%（全部过期）
       ↓ 100%
    DB QPS = 10 万
    → DB 崩溃
```

### 2.3 解决：错峰过期

```
方案 1：过期时间加随机偏移
  SETEX key 3600 + random(0, 600)
  → key 过期时间分散到 1h ± 10min
  → 不会同时过期

方案 2：分层过期
  - 短 TTL（5 分钟）
  - 后台异步刷新（定时任务延长期）

方案 3：永不过期 + 主动更新
  - key 不设 TTL
  - 后台任务主动刷新
  - 写时主动更新
```

### 2.4 解决：高可用兜底

```
Redis Cluster：
  - 多副本（主从）
  - Sentinel / Cluster 自动故障转移

多级缓存：
  - 即使 Redis 全挂，还有 Nginx / 进程内
  - 真正兜底是 DB（限流保护）

熔断降级：
  - DB 压力大时熔断
  - 返回兜底数据
  - 见 circuit-breaker.md
```

## 3. 缓存穿透

### 3.1 什么是穿透？

```
场景：
  - 查询 key = -1（不存在的用户）
  - 缓存 miss → 查 DB
  - DB 也 miss → 返回空
  - 但恶意请求大量查不存在的 key
  - 每次都穿透到 DB
  → DB 被无效请求打死

特点：
  - 缓存和 DB 都没有
  - 大量重复无效请求
```

### 3.2 穿透示意

```
  客户端恶意请求：/api/user?id=-1
  Redis: miss
  ↓
  MySQL: SELECT * FROM user WHERE id = -1 → null
  ↓
  返回 null

每秒 1 万次这种请求 → DB 死
```

### 3.3 解决：缓存空值

```
缓存不存在的数据：
  - 第一次查 DB miss → 缓存空值（标记不存在）
  - 第二次查 → 命中缓存（空值）→ 直接返回

实现：
  - SETEX key "null" 60
  - 短 TTL（60s，避免长期占内存）

注意：
  - 真实用户和恶意请求都受益
  - 但大量不同 key 的空值会占内存
```

### 3.4 解决：布隆过滤器

```
原理：
  - 用布隆过滤器记录所有存在的 key
  - 请求来时先过布隆过滤器
  - 不在过滤器 → 直接返回（一定不存在）
  - 在过滤器 → 走缓存 / DB 流程

特点：
  - 空间效率极高（1 亿 key 仅需 100 MB）
  - 存在误判率（不在的可能判为在，约 1%）

实现：
  - RedisBloom 模块
  - Guava BloomFilter（Java）
  - 自实现（位数组 + 多个 hash）
```

### 3.5 解决：参数校验

```
前置校验：
  - Controller 层校验参数合法性
  - 不合法直接返回 400
  - 例：id 必须 > 0

效果：
  - 拦截 80% 恶意 / 错误请求
  - 减轻下游压力
```

## 4. 缓存击穿

### 4.1 什么是击穿？

```
场景：
  - 热点 key（爆款商品 / 热门新闻）
  - 过期瞬间大量并发请求
  - 都 miss → 都查 DB
  - DB 被瞬间冲垮

与雪崩区别：
  - 雪崩：大量 key 同时过期
  - 击穿：单个热点 key 过期

📌 击穿是"集中爆发的单点"
```

### 4.2 击穿示意

```
  热点商品 X，过期时间到：
    t0: key 过期
    t1: 1000 个请求同时进来
    t2: 1000 个请求都 miss
    t3: 1000 个请求都查 DB
    t4: DB 被打爆
```

### 4.3 解决：互斥锁（分布式锁）

```
思路：
  - miss 后只让一个线程查 DB
  - 其他线程等待
  - 查完写回缓存，其他线程读缓存

实现：
  1. miss
  2. SETNX lock:key 1  // 加锁
  3. 拿到锁：查 DB + 写缓存 + 释放锁
  4. 没拿到锁：sleep + 重试 + 再查缓存

代码（伪）：
  lock = redis.setnx("lock:key", 1, 30s)
  if (lock) {
    value = db.get(key)
    redis.set(key, value)
    redis.del("lock:key")
  } else {
    sleep(100ms)
    return cache.get(key)  // 这时应该有值
  }
```

### 4.4 解决：永不过期 + 异步刷新

```
思路：
  - 热点 key 不设 TTL
  - 后台任务定期刷新值
  - 读时永远命中

实现：
  - 设置时 value = 业务值 + expire_time
  - 读时发现 expire_time 临近 → 异步刷新

📌 适合"必须热点"的场景
```

### 4.5 解决：逻辑过期

```
思路：
  - 不设 Redis TTL
  - value 里带 expire_time 字段
  - 读时检查是否过期
  - 过期则加锁异步刷新

实现：
  - value = {data: {...}, expire: 1700000000}
  - 读时：now > expire → 加锁 + 异步刷新
  - 返回旧值（保证可用）

📌 牺牲强一致，换可用性
```

## 5. 三大问题对比

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│              │ 雪崩         │ 穿透         │ 击穿         │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 触发         │ 大量 key     │ 不存在 key   │ 单个热点     │
│              │ 同时过期     │              │ key 过期     │
│ 请求类型     │ 正常请求     │ 恶意 / 错误  │ 正常请求     │
│ 缓存状态     │ 有 → 无      │ 一直无       │ 有 → 无      │
│ DB 状态      │ 有           │ 无           │ 有           │
│ 解决方案     │ 错峰过期     │ 布隆过滤器   │ 分布式锁     │
│              │ 高可用       │ 空值缓存     │ 永不过期     │
│              │ 熔断降级     │ 参数校验     │ 逻辑过期     │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

## 6. 解决：综合方案

```
完整防御：

1. 错峰过期（防雪崩）：
   - TTL 加随机偏移

2. 布隆过滤器（防穿透）：
   - 不存在 key 直接拦截

3. 分布式锁（防击穿）：
   - 热点 key miss 时单线程回源

4. 多级缓存（兜底）：
   - Redis 挂了还有进程内

5. 熔断降级（兜底）：
   - DB 压力大时熔断

6. 限流（兜底）：
   - 入口限制请求量

📌 多重防御，纵深防御
```

## 8. 一句话总结

```
📌 三大问题都会打爆 DB，但触发原因和解决方案不同
📌 雪崩：大量 key 同时过期 → 错峰过期 + 高可用 + 熔断
📌 穿透：查不存在的 key → 布隆过滤器 + 空值缓存 + 参数校验
📌 击穿：热点 key 过期瞬间 → 分布式锁 + 永不过期 + 逻辑过期
📌 综合防御 = 多个方案组合（纵深防御）
📌 监控 Redis miss rate 和 DB QPS，及时发现穿透 / 击穿
```
