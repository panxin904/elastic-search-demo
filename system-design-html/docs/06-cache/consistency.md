# 缓存一致性

> 当 DB 和缓存都有数据时，**如何保证两边一致**？

## 1. 一致性的本质

```
单一数据源原则：
  同一份数据应该只有一个权威来源

分布式场景：
  DB 是权威（事务保证）
  缓存是性能优化（最终一致即可）

📌 缓存一致性 = 在合理延迟内让缓存与 DB 同步
   不要求实时一致（那不如直接查 DB）
```

## 2. 写 DB 后如何同步缓存？

### 2.1 三种策略

```
策略 1：先更新 DB，再更新缓存
策略 2：先更新 DB，再删除缓存
策略 3：先删除缓存，再更新 DB

📌 业界共识：策略 2 最常用
```

### 2.2 策略 1：先更新 DB，再更新缓存（不推荐）

```
1. 写 DB = 5
2. 更新缓存 = 5
3. 返回

问题：
  - 两次写非原子（中间崩溃 → DB=5, 缓存=旧）
  - 并发写 A=5, B=6 时序颠倒 → 缓存可能=A 但 DB=B
  - 浪费资源（缓存可能根本不会被读）

📌 不推荐
```

### 2.3 策略 2：先更新 DB，再删除缓存（Cache-Aside）

```
1. 写 DB = 5
2. 删除缓存
3. 返回

下次读：
  1. miss → 查 DB → 写缓存 = 5

优点：
  - 实现简单
  - 即使删缓存失败，下次读也能从 DB 加载新值
  - 没有"双写非原子"问题

问题：
  - 并发场景仍可能不一致
```

### 2.4 策略 3：先删除缓存，再更新 DB

```
1. 删除缓存
2. 写 DB = 5
3. 返回

问题：
  - 删完缓存到写完 DB 之间，读到旧值并写回缓存
  - 最终缓存=旧值，DB=新值
  - 不一致

📌 比策略 2 风险更高
   除非配合"延迟双删"
```

## 3. Cache-Aside 的不一致分析

### 3.1 经典不一致场景

```
线程 A 写：1. 写 DB = 5   2. 删缓存
线程 B 读：               1. 读缓存 miss
                          2. 读 DB = 4（旧值）
线程 A 删缓存：           
线程 B 写缓存：3. 写缓存 = 4（旧值）

时序：
  t0: A 写 DB = 5
  t1: B 读缓存 miss
  t2: B 读 DB = 4（旧值！）
  t3: A 删缓存
  t4: B 写缓存 = 4
  → 缓存是旧值，DB 是新值

📌 这是 Cache-Aside 经典的不一致场景
```

### 3.2 发生条件

```
B 的"读 DB + 写缓存"必须跨越 A 的"写 DB + 删缓存"
即：B 的整个读流程要慢于 A 的整个写流程

实际发生概率：
  - 读耗时 > 写耗时时：可能
  - 通常读比写快（缓存命中是 ns 级）
  - 但跨实例、跨网络时仍可能

📌 不一致是小概率但确实存在的
```

## 4. 解决：延迟双删

```
策略 2 增强版：
  1. 删缓存
  2. 写 DB
  3. 延迟 N 毫秒（500ms-1s）
  4. 再删缓存

时序：
  t0: 删缓存
  t1: 写 DB = 5
  t2: B 读缓存 miss
  t3: B 读 DB = 4（旧值）
  t4: B 写缓存 = 4
  t5: 第二次删缓存 ← 这里再删一次，B 写的旧值被清除
  → 缓存最终是新的 miss，下次读会从 DB 加载新值

📌 延迟时间要 > 业务最大读耗时
```

## 5. 解决：基于 MQ 的异步失效

```
1. 写 DB（带 binlog 或通知）
2. 发消息到 MQ：失效 key
3. MQ 消费者收到消息
4. 失效缓存

优点：
  - 异步、不阻塞写
  - 多消费者保证可靠
  - 顺序保证（同 key 顺序失效）

缺点：
  - 引入 MQ 复杂度
  - 消息延迟
```

## 6. 解决：基于 binlog 的同步

```
1. 应用写 DB
2. Canal 订阅 binlog
3. 解析出变更的 key
4. 失效 Redis 缓存

优点：
  - 应用无侵入
  - 自动同步
  - 与事务一致（binlog 顺序）

缺点：
  - 引入 Canal / Debezium
  - 运维成本
  - 解析延迟

📌 阿里大规模使用的方案
```

## 7. 强一致方案：分布式锁

```
场景：
  任何时刻只允许一个线程读写缓存和 DB

实现：
  1. 获取分布式锁（Redis / ZK）
  2. 写 DB
  3. 删缓存
  4. 释放锁

代价：
  - 性能差（锁开销）
  - 死锁风险
  - 复杂度高

📌 只用于强一致场景（金融账务）
```

## 8. 最终一致性方案对比

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 方案         │ 复杂度       │ 延迟         │ 可靠性       │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 失效缓存     │ 极低         │ 0（删瞬间）  │ 可能不一致   │
│ 延迟双删     │ 低           │ 500ms-1s     │ 一致性更好   │
│ MQ 异步失效  │ 中           │ 秒级         │ 较好         │
│ Binlog 同步  │ 高           │ 秒级         │ 高           │
│ 分布式锁     │ 高           │ 同步等待     │ 强一致       │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

## 9. 实战：电商缓存一致性

### 9.1 商品详情

```
数据特点：
  - 读多写少
  - 写不频繁（商家改价、上下架）
  - 一致性要求中等（价格偶尔不一致可接受）

方案：延迟双删
  1. 删缓存
  2. 写 DB
  3. 延迟 1s 再删缓存

容忍：1s 内的不一致
```

### 9.2 库存

```
数据特点：
  - 读写都多
  - 一致性要求高（超卖问题）
  - 实时性强

方案：
  1. Redis 原子操作扣减（Lua）
  2. 异步同步到 DB
  3. DB 是权威，Redis 是预扣

📌 不能只用缓存一致性方案
   库存要 Redis Lua 原子操作保证
```

### 9.3 用户资料

```
数据特点：
  - 读写都多
  - 一致性要求高（昵称 / 头像错乱体验差）

方案：Binlog 同步
  1. 应用写 DB
  2. Canal 订阅 binlog
  3. 失效 Redis

容忍：秒级不一致
```

## 10. 缓存不一致的监控

```
监控项：
  1. 缓存与 DB 一致性检查（定时任务对比）
  2. 缓存命中率异常下降
  3. 缓存 key 频繁失效
  4. 写入耗时（可能卡在删缓存）

告警：
  - 不一致率 > 阈值 → 告警
  - 命中率突降 → 可能大面积不一致
```

## 11. 一致性与可用性的取舍

```
强一致 + 低可用：
  - 分布式锁
  - 写时读阻塞

最终一致 + 高可用：
  - 失效缓存
  - 异步同步

📌 99% 业务选最终一致
   强一致只用在金融账务 / 库存扣减
```

## 12. 一句话总结

```
📌 缓存一致性 = 在合理延迟内让缓存与 DB 同步
📌 主流策略：先写 DB，再删缓存（Cache-Aside）
📌 经典不一致场景：B 读旧值后写回缓存
📌 解决：延迟双删 / MQ 异步失效 / Binlog 同步 / 分布式锁
📌 选型看一致性要求和延迟容忍度
📌 99% 业务用最终一致（秒级延迟可接受）
📌 强一致用分布式锁，但性能差
```
