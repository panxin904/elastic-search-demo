# 热点 Key

> 少量 key 占据绝大部分流量，**单 key 性能成为瓶颈**。

## 1. 什么是热点 Key？

```
流量分布：
  - 100 万个商品
  - 但 1% 的商品（1 万个）占据 99% 的访问
  - 这 1 万个就是热点 Key

特征：
  - 流量集中（远超平均）
  - 单点压力极大
  - 可能引发雪崩

典型场景：
  - 秒杀爆款
  - 网红直播
  - 热点新闻
  - 大 V 发帖
  - 排行榜
```

## 2. 热点 Key 的危害

### 2.1 单 Redis 节点压力

```
Redis Cluster（16384 slot）：
  - key 通过 hash 落到某个 slot
  - 该 slot 在某个 Redis 节点

热点 key → 单个节点 QPS 极高：
  - Redis 单节点 10 万 QPS 上限
  - 热点 key 单节点可能 50 万 QPS
  - 节点崩溃
```

### 2.2 带宽瓶颈

```
单 key 访问：
  - key=10KB → 10 万 QPS = 1 GB/s 流量
  - 单节点网卡打满
  - 其他请求受影响
```

### 2.3 击穿源

```
热点 key 过期瞬间：
  - 大量请求同时 miss
  - 都打到 DB
  - DB 崩溃
  → 见 three-problems.md 的"击穿"
```

## 3. 热点 Key 检测

### 3.1 离线分析

```
日志分析：
  - 收集访问日志
  - 按 key 聚合
  - 找出 Top N

工具：
  - ELK / ClickHouse 分析
  - 自研数据管道

缺点：实时性差（T+1）
```

### 3.2 在线探测

```
Redis 4.0+：
  redis-cli --hotkeys
  - 扫描所有 key
  - 统计访问频率

缺点：
  - 影响性能
  - 只能本地实例
```

### 3.3 proxy 探测

```
方案：
  - 在 Redis proxy（如 Codis / Twemproxy）层统计
  - 实时聚合 key 访问次数
  - 超过阈值告警

代表：
  - CacheCloud（搜狐）
  - 自研 proxy
```

### 3.4 客户端埋点

```
方案：
  - 客户端 SDK 统计 key 访问
  - 定时上报
  - 聚合发现热点

优点：实时
缺点：客户端耦合
```

## 4. 热点 Key 解决方案

### 4.1 多级缓存

```
热点 key 副本放进程内：
  - 本地缓存 1000 个热点 key
  - 优先读本地
  - Redis 只处理"次热"key

实现：
  - 启动时拉取热点 key 列表
  - 持续更新
  - LRU 淘汰
```

### 4.2 Key 分散（Key Spreading）

```
思路：
  - 把一个 key 拆成多个
  - 例如：product:10086 → product:10086:1, product:10086:2, ...
  - 写入多个 key
  - 读取时随机选一个

实现：
  - set key:{i} value, i ∈ random(0, N-1)
  - get key:{random(0, N-1)}

代价：
  - 一致性差（删除要全删）
  - 实现复杂

📌 仅在极端场景使用
```

### 4.3 副本集（Hot Key Replica）

```
思路：
  - 同一 key 复制多份
  - 写时全部写
  - 读时随机选一个

实现（Redis）：
  - 主 key + N 个副本 key
  - 写时全写
  - 读时 random(0, N) 选

优点：
  - 简单
  - 一致性可保证（写全写）

缺点：
  - 写入放大
  - 副本同步延迟
```

### 4.4 读写分离 + 副本读

```
思路：
  - 主从复制下
  - 热点 key 读流量分散到多个从节点
  - 主节点只写

实现：
  - 客户端随机选从节点读
  - 主从延迟敏感时不用
```

### 4.5 客户端缓存 + 后台同步

```
思路：
  - 客户端缓存热点 key 值
  - 后台异步刷新
  - 读时优先本地

实现：
  - 本地 Map + TTL
  - 后台 worker 定期 GET
  - 失效时再请求 Redis

📌 适合读多写少
   强一致场景不适用
```

### 4.6 服务端预热

```
思路：
  - 识别热点后，主动预热到本地
  - 全量推到所有应用实例

实现：
  - 配置中心推送热点列表
  - 应用收到后拉数据到本地
```

## 5. 实战方案

### 5.1 秒杀场景

```
商品 ID = 10086，预期 100 万 QPS

方案：
  - Redis 预扣库存（Lua 原子）
  - 多副本 + 读写分离
  - Nginx 进程内缓存商品信息
  - 网关层限流到 50 万 QPS
  - 用户侧排队
```

### 5.2 热点新闻

```
新闻 ID = news:888，每秒 100 万 PV

方案：
  - 静态化（HTML 推到 CDN）
  - CDN 抗 99% 流量
  - 边缘节点 + 多副本
  - Redis 只承担边角请求
```

### 5.3 大 V 发帖

```
明星 ID = star:001，每条微博 1000 万阅读

方案：
  - 帖子静态化
  - Feed 流用混合模式（推 + 拉）
  - 见 feed-stream.md
```

## 6. 防患于未然

### 6.1 预防性设计

```
1. 缓存粒度合理：
   - 太细：命中率低
   - 太粗：热点放大
   - 选业务"自然粒度"

2. 流量预估：
   - 大促前预热
   - 容量评估

3. 多副本：
   - 关键 key 提前做副本
   - 监控自动触发
```

### 6.2 监控告警

```
必须监控：
  - 单 key QPS（超过阈值告警）
  - Redis 节点 QPS（倾斜预警）
  - 节点 CPU / 网络（瓶颈预警）

告警策略：
  - 单 key QPS > 10 万 → 告警
  - 节点 QPS > 80% → 告警
```

## 7. 一句话总结

```
📌 热点 Key = 少数 key 占据绝大部分流量
📌 危害：单节点压力 + 带宽瓶颈 + 击穿源
📌 检测：proxy 探测 / 客户端埋点 / 离线分析
📌 解决：多级缓存 + Key 分散 + 副本集 + 读写分离
📌 实战：秒杀用 Redis Lua + 限流；热点新闻用 CDN
📌 预防：合理粒度 + 预热 + 监控告警
📌 业务侧要预估热点，提前压测
```
