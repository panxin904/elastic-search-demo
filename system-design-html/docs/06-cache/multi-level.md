# 多级缓存架构

> 从浏览器到数据库，每一层都有自己的缓存。**组合得当才能发挥最大效果**。

## 1. 多级缓存全景

```
┌──────────────────────────────────────────────────────┐
│ 浏览器缓存 (Browser Cache)                            │
│   - HTTP Cache-Control / ETag                        │
│   - LocalStorage / SessionStorage                    │
│   - Service Worker                                   │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│ CDN 缓存                                              │
│   - 静态资源（JS / CSS / 图片 / 视频）                 │
│   - 边缘计算                                         │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│ 反向代理 / Nginx 缓存                                  │
│   - proxy_cache                                      │
│   - Lua 缓存                                         │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│ 应用进程内缓存                                          │
│   - JVM Heap (Caffeine / Guava Cache)                │
│   - Python lru_cache                                 │
│   - Go sync.Map                                      │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│ 分布式缓存                                            │
│   - Redis Cluster / Memcached                        │
│   - Tair                                             │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│ 数据库缓存                                            │

│   - SSD / NVMe                                       │

```

## 2. 各级缓存的对比

```
┌──────────────┬──────────┬──────────┬──────────┬──────────┐
│ 层级         │ 容量     │ 速度     │ 成本     │ 共享     │
├──────────────┼──────────┼──────────┼──────────┼──────────┤
│ 浏览器       │ MB       │ ns       │ 0        │ 否       │
│ CDN          │ PB       │ ms       │ 中       │ 是       │
│ Nginx        │ GB       │ μs       │ 低       │ 否       │
│ 进程内       │ GB       │ ns       │ 0        │ 否       │
│ Redis        │ TB       │ ms       │ 中       │ 是       │
│ 数据库       │ GB       │ ms       │ 高       │ 否       │
└──────────────┴──────────┴──────────┴──────────┴──────────┘

📌 越上层越快越小，越下层越慢越大
   - 容量：上层 < 下层
   - 速度：上层 > 下层
   - 共享：上层 < 下层
```

## 3. 各级缓存详解

### 3.1 浏览器缓存

```
HTTP Header 控制：
  - Cache-Control: max-age=3600
  - Expires: Thu, 01 Jan 2026 00:00:00 GMT
  - ETag: "abc123"
  - Last-Modified: Mon, 01 Jan 2026 ...

策略：
  - 强缓存：max-age 内直接用本地缓存
  - 协商缓存：max-age 过期后，用 ETag / Last-Modified 与服务器验证

适用：
  - 静态资源（JS/CSS/图片）→ 强缓存（30 天）
  - HTML → 协商缓存
  - API → 通常不缓存或短缓存
```

### 3.2 CDN 缓存

```
原理：
  - 边缘节点缓存源站内容
  - 用户就近访问
  - 命中率高时源站压力极小

适用：
  - 静态资源
  - HTML（短 TTL）
  - 公开 API

不适用：
  - 个性化内容（按用户）
  - 实时数据
  - 大文件流（视频按需用）
```

### 3.3 Nginx 缓存

```
proxy_cache：
  - Nginx 反向代理层缓存
  - 可缓存后端响应
  - 配置灵活

Lua 缓存（如 OpenResty）：
  - 在请求处理阶段缓存
  - 可以做复杂的逻辑

适用：
  - 反向代理后的 API 缓存
  - 减少后端服务压力
```

### 3.4 进程内缓存

```
特点：
  - 最快（ns 级）
  - 不跨进程
  - 容量受 JVM 堆限制

实现：
  - Java：Caffeine（推荐）、Guava Cache
  - Python：functools.lru_cache
  - Go：sync.Map、ristretto

适用：
  - 字典数据（地区 / 类别）
  - 配置（启动时加载）
  - 高频小数据

陷阱：
  - 多实例不一致（每实例一份缓存）
  - 内存占用大
  - GC 压力
```

### 3.5 Redis 分布式缓存

```
特点：
  - 跨进程共享
  - 容量大（TB 级）
  - 速度中等（ms 级）

适用：
  - 会话（Session）
  - 热点数据
  - 排行榜 / 计数器
  - 分布式锁

📌 Redis Cluster 已经是事实标准
```

### 3.6 数据库缓存

```
InnoDB Buffer Pool：
  - MySQL 默认缓存热点数据页
  - 通常配 60-80% 内存
  - 自动管理（LRU 变种）

优化：
  - 增大 Buffer Pool（多留内存）
  - 热点数据放内存
  - 减少磁盘 IO
```

## 4. 多级缓存架构

### 4.1 典型架构

```
请求从用户到数据库：

Browser Cache → CDN → Nginx → Process Cache → Redis → DB

每层 miss 则下一层：
  - Browser miss → 请求到 CDN
  - CDN miss → 请求到 Nginx
  - Nginx miss → 请求到应用
  - 应用 miss → 查 Redis
  - Redis miss → 查 DB
  - DB miss → 返回空

写入时反向：
  - 写 DB
  - 失效 Redis
  - 失效进程内（过期 / 主动清理）
  - 失效 Nginx（purge）
  - CDN 靠 TTL 过期
```

### 4.2 命中率优化

```
目标：每层命中率最大化

Browser：90%+（静态资源）
CDN：80%+（热门资源）
Nginx：50%+（API 缓存）
进程内：80%+（字典 / 配置）
Redis：80%+（热点数据）
DB：兜底

📌 总命中率 = 1 - (1 - p1)(1 - p2)(1 - p3)...
   每层 80% → 总体 99.2%
```

## 5. 一致性问题

### 5.1 多级缓存的数据同步

```
挑战：
  写 DB 后，每层都要失效
  异步失效有时间窗口
  → 多级缓存之间可能不一致

例：
  1. 用户更新资料（写 DB）
  2. 失效 Redis
  3. 进程内缓存还没失效
  4. 用户刷新 → 进程内命中旧数据

📌 多级缓存 = 多倍不一致风险
```

### 5.2 解决：分层失效策略

```
DB → Redis → 进程内 → Nginx → CDN

DB 是权威：写完就以 DB 为准
Redis：写后立即失效（消息广播 / 主动删）
进程内：短 TTL（即使不一致也很快过期）
Nginx：purge（主动失效）
CDN：靠 TTL（几分钟过期）

📌 越下层越严格，越上层越宽松
```

## 6. 进程内缓存 vs Redis

```
选进程内：
  - 数据量小
  - 不跨实例
  - 极致性能

选 Redis：
  - 数据量大
  - 必须共享
  - 跨实例一致

📌 实际生产都是组合用
   进程内放小字典，Redis 放热点数据
```

## 7. 缓存预热

```
冷启动问题：
  - 服务刚启动，缓存都是空的
  - 第一波请求全部穿透到 DB
  → DB 被打爆

预热方案：
  1. 启动时加载字典到进程内
  2. 启动时从 DB 加载热点数据到 Redis
  3. 灰度发布（先发布 1 台观察）
  4. 用 Redis Cluster 的 slot 同步
```

## 8. 缓存淘汰策略

```
进程内缓存：
  - LRU（最近最少使用）
  - LFU（最近最不常用）
  - FIFO（先进先出）
  - 过期时间（TTL）

Redis：
  - allkeys-lru：所有 key LRU
  - volatile-lru：仅过期 key LRU
  - allkeys-lfu：所有 key LFU
  - volatile-ttl：过期时间短的优先
  - noeviction：不淘汰（写满报错）

📌 推荐：allkeys-lru（最常用）或 allkeys-lfu
```

## 9. 工程实践

### 9.1 缓存设计原则

```
1. 越热的数据越靠近上层
2. 一致性要求高的数据靠近 DB
3. 静态资源全部推到 CDN
4. 进程内只放只读字典
5. Redis 放高频可变数据
6. 每层都有 TTL 兜底
```

### 9.2 监控指标

```
必须监控：
  - 每层命中率
  - 每层容量 / 使用率
  - 慢查询（穿透到底层）
  - 大 key / 热 key

告警：
  - 命中率突降
  - Redis 内存满
  - DB QPS 突增（穿透预警）
```

### 9.3 实战陷阱

```
陷阱 1：缓存层过多
  - 5 层以上难维护
  - 失效链路复杂
  - 一般 3 层足够

陷阱 2：命中率不达标
  - 缓存粒度太细（每个字段一个 key）
  - 命中率反而低

陷阱 3：缓存雪崩
  - 大量 key 同时过期
  - DB 被穿透
  → 错峰过期 + 后台刷新
```

## 10. 一句话总结

```
📌 多级缓存 = Browser + CDN + Nginx + 进程内 + Redis + DB
📌 越上层越快越小，越下层越慢越大
📌 命中率高（每层 80%），总体命中 99%+
📌 多级缓存 = 多倍不一致风险，必须有分层失效策略
📌 进程内 vs Redis：字典 / 配置用进程内，热点共享用 Redis
📌 缓存预热解决冷启动问题
📌 监控每层命中率、容量、淘汰策略
```
