# 🏗️ 分布式架构模式

> 分布式系统的**架构演进**与**典型模式**。

## 🧩 典型架构模式

### 1. 微服务架构（Microservices）

**特点：** 小而自治、独立部署、去中心化

| 优点 | 缺点 |
|---|---|
| 独立部署 / 扩容 | 运维复杂度高 |
| 技术栈灵活 | 分布式事务难题 |
| 故障隔离 | 调用链追踪难 |
| 适合大型团队 | 服务治理成本高 |

**Spring Cloud / Dubbo / gRPC 是典型实现**

### 2. SOA（Service-Oriented Architecture）

**特点：** 面向服务的架构，通过 ESB（企业服务总线）连接

```
   服务A ─┐
   服务B ─┼→ ESB → 服务消费者
   服务C ─┘
```

| 维度 | SOA | 微服务 |
|---|---|---|
| 服务粒度 | 较粗（业务能力） | 细（单一职责） |
| 通信方式 | ESB（重量级） | HTTP/RPC（轻量） |
| 数据存储 | 共享数据库 | 每个服务独立数据库 |
| 部署 | 单体部署多见 | 独立部署 |
| 适用 | 企业级集成 | 互联网大规模应用 |

### 3. 事件驱动架构（EDA）

**特点：** 通过事件（Event）解耦服务

```
下单服务 ──发布 OrderCreated──→ MQ ──订阅→ 库存服务、支付服务、物流服务
```

| 优点 | 缺点 |
|---|---|
| 高度解耦 | 调试困难 |
| 天然异步 | 事件顺序难保证 |
| 易扩展 | 数据最终一致 |
| 适合复杂业务流程 | 需要幂等设计 |

### 4. CQRS（Command Query Responsibility Segregation）

**特点：** 读写分离，写一个模型、读另一个模型

```
写 → Command → 写库 → 同步 → 读库（可能经过 ES）→ Query → 读
```

| 适用场景 | 不适用场景 |
|---|---|
| 读多写少 | 数据频繁修改 |
| 复杂查询 | 强实时一致 |
| 报表分析 | 简单业务 |

### 5. Saga 长事务

**特点：** 将分布式事务拆为多个本地事务 + 补偿

```
T1 成功 → T2 成功 → T3 失败 → C3 补偿 → C2 补偿 → C1 补偿
       编排（Orchestration）/ 协调（Choreography）
```

**Seata、ServiceComb Saga 是典型实现**

### 6. Sidecar 模式

**特点：** 把通用能力（服务发现、限流、监控）抽到独立的 Sidecar 进程

```
应用 Pod ┐
         ├→ localhost:15001（Sidecar 通信）
sidecar ┘
```

**Service Mesh（Istio / Linkerd）就是 Sidecar 的标准化**

## 🌐 服务间通信方式

### 同步调用

| 协议 | 特点 | 场景 |
|---|---|---|
| **HTTP/REST** | 通用、易调试 | 跨语言、外部 API |
| **gRPC** | 高性能、强类型 | 内部服务 |
| **Dubbo RPC** | 阿里生态、高性能 | Java 微服务 |
| **WebService/SOAP** | 老牌、重量级 | 企业遗留 |

### 异步通信

| 中间件 | 特点 |
|---|---|
| **Kafka** | 高吞吐、日志 / 事件流 |
| **RocketMQ** | 事务消息、阿里生态 |
| **RabbitMQ** | 灵活的路由、复杂业务 |
| **Pulsar** | 分层存储、云原生 |

## 🏛️ 微服务拆分原则

| 原则 | 说明 |
|---|---|
| **单一职责** | 一个服务只做一件事 |
| **业务边界** | 按业务能力（订单/库存/支付）拆分 |
| **数据独立** | 每个服务独占数据库 |
| **服务大小** | 2 Pizza Team（亚马逊）能维护的规模 |
| **演进式拆分** | 不要一上来就拆，先单体后微服务 |

## 🔧 分布式系统常见问题

| 问题 | 含义 | 解决方案 |
|---|---|---|
| **服务雪崩** | 一个服务挂掉引发整链路崩溃 | 熔断、降级、限流、超时 |
| **数据不一致** | 多副本数据不一致 | CAP 选择、最终一致、分布式事务 |
| **调用链追踪** | 跨服务调用难追踪 | Sleuth、Zipkin、SkyWalking |
| **服务依赖** | 服务依赖关系复杂 | 依赖图、熔断、版本管理 |
| **配置分散** | 配置散落在各服务 | 配置中心（Nacos、Apollo）|
| **日志分散** | 日志在多个节点 | ELK、Loki |

## 🎯 实际架构示例

**电商系统最终架构**

```
                     客户端（Web / H5 / App）
                            ↓
                       CDN + WAF
                            ↓
                    Nginx / SLB（负载均衡）
                            ↓
                   Spring Cloud Gateway（API 网关）
                ┌───────┬───────┬────────┬────────┐
                ↓       ↓       ↓        ↓        ↓
             用户服务  商品服务  订单服务  支付服务  营销服务
                ↓       ↓       ↓        ↓        ↓
             MySQL    MySQL    MySQL    MySQL    MySQL
               │        │       │         │
               └────────┴───────┴─────────┘
                              ↓
                         Nacos（注册中心 + 配置中心）
                              ↓
                         Sentinel（限流熔断）
                              ↓
                          Seata（分布式事务）
                              ↓
                         RocketMQ / Kafka（异步消息）
                              ↓
                          ELK（日志） + SkyWalking（链路追踪）
```
