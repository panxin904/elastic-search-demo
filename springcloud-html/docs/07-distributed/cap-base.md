# ⚖️ CAP 与 BASE 理论

> 分布式系统的**理论基础**，决定了架构设计的取舍。

## 🎯 CAP 定理

**CAP** 是分布式系统的**三个核心特性**，三者**最多只能满足两个**，不可能三者兼得。

| 特性 | 英文 | 含义 |
|---|---|---|
| **C** | Consistency 一致性 | 所有节点在同一时刻看到的数据完全相同（强一致性）|
| **A** | Availability 可用性 | 每个请求都能得到响应（不保证数据最新）|
| **P** | Partition tolerance 分区容错 | 网络分区（部分节点失联）时系统仍能提供服务 |

> **关键洞察**：网络分区是**物理不可避免**的，所以分布式系统**必须选 P**，再在 C 和 A 之间权衡。

### 📊 CAP 取舍示例

```
                    强一致性 (C)
                         ▲
                        /│\
                       / │ \
                      /  │  \
                     /   │   \
                    /    │    \
                   /  CP │ CA  \
                  /  弱A  │  弱C  \
                 /        │        \
                ▼─────────┼─────────▼
            分区容错 (P)         可用性 (A)
```

| 组合 | 含义 | 典型系统 |
|---|---|---|
| **CA**（放弃 P）| 不允许分区 → 单点 / 主从同步复制 | 传统单机 DB、主备集群 |
| **CP**（放弃 A）| 分区时停止服务保证一致 | ZooKeeper、etcd、HBase、Redis Cluster |
| **AP**（放弃 C）| 分区时继续服务，最终一致 | Eureka、Cassandra、DynamoDB |

### 🛒 实际案例：电商下单

```
正常情况：客户端 → Gateway → 订单服务 + 库存服务 → MySQL（强一致）
网络分区：订单服务与库存服务断开
  - CP 策略：订单服务返回错误"暂不可用"（保证库存不超卖）
  - AP 策略：先下单成功，库存异步扣减（可能短暂超卖，最终一致）
```

> 业务侧权衡：库存**不能超卖**（CP） vs 订单**不能失败**（AP）

## 🌿 BASE 理论

**BASE** 是 **CAP 中选 AP** 后的工程实践，由 eBay 提出。

| 字母 | 全称 | 含义 |
|---|---|---|
| **BA** | Basically Available 基本可用 | 分区时允许损失部分可用性（响应慢、功能降级）|
| **S** | Soft State 软状态 | 允许中间状态（数据副本间短暂不一致）|
| **E** | Eventually Consistent 最终一致性 | 经过一段时间后所有副本达到一致 |

### 📌 基本可用（BA）的表现形式

| 形式 | 含义 | 示例 |
|---|---|---|
| **响应时间延长** | 正常 100ms → 分区时 1-2s | 大促期间页面加载变慢 |
| **功能降级** | 关闭非核心功能 | 关闭评论、推荐，只保留核心下单 |
| **服务限流** | 拒绝部分请求 | 返回"系统繁忙请稍后再试" |

### 🔄 最终一致性的实现方式

| 方式 | 原理 | 时延 |
|---|---|---|
| **异步复制** | 主写成功后异步同步到从 | 秒级 |
| **消息队列** | 通过 MQ 异步通知其他系统 | 秒级 |
| **定时校对** | 后台任务定时比对并修复 | 分钟级/小时级 |
| **冲突解决** | CRDT、向量时钟、Last-Write-Win | 实时 |

## ⚖️ 一致性模型对比

| 模型 | 含义 | 实现 | 性能 |
|---|---|---|---|
| **强一致性** | 写后立即读到最新值 | 同步阻塞、Paxos/Raft | 低 |
| **弱一致性** | 不保证能读到最新 | 异步复制 | 高 |
| **最终一致性** | 经过一段时间后读到 | BASE 各种实现 | 中 |
| **因果一致性** | 有因果关系的操作顺序一致 | 向量时钟 | 中 |
| **读己之写** | 自己写的数据自己能读到 | 会话保持 | 中 |

## 🎯 一致性 vs 可用性的取舍策略

### 选 CP 的场景（强一致）
- **金融交易**：转账、支付不能出错
- **库存扣减**：超卖 = 资损
- **分布式锁**：多节点协调不能错

### 选 AP 的场景（最终一致）
- **社交动态**：点赞、评论可以延迟
- **用户资料**：头像、昵称可以延迟
- **日志分析**：可以接受部分丢失

## 🔗 实际架构中的混合策略

```
                业务分类                一致性策略
                
                资金 / 库存   ──────→   CP（强一致）
                   ↓
                用户资料 / 评论 ──────→  AP（最终一致）
                   ↓
                日志 / 分析   ──────→   AP（允许少量丢失）
```

**实例：电商系统的混合一致性**

| 模块 | 策略 | 技术 |
|---|---|---|
| 下单扣库存 | CP | MySQL 事务 + Redis Lua 原子 |
| 支付结算 | CP | 分布式事务 Seata AT/TCC |
| 积分赠送 | AP | MQ 异步 + 定时校对 |
| 订单查询 | 读己之写 | 会话粘性 + 缓存失效 |
| 物流推送 | AP | MQ 异步通知 |

## 📚 经典问题（FLP 不可能）

CAP 之外还有一个重要理论：**FLP 不可能性**（1985 年）。

- 在**异步网络**中，即使**只有一个节点故障**，**不存在**一个确定性算法能在**有限时间**内达成共识。
- 实际系统（Paxos / Raft）通过**超时机制**绕过 FLP 的"异步"前提。

## 🎓 面试高频问题

| 问题 | 关键点 |
|---|---|
| CAP 是什么？| C 一致 / A 可用 / P 分区容错，三选二 |
| 为什么不能三者兼得？| 网络分区必然存在时，C 和 A 互斥 |
| BASE 是什么？| 基本可用 + 软状态 + 最终一致，CAP 中选 AP 的实践 |
| 你的项目是 CP 还是 AP？| 按业务模块分类说明 |
| 一致性模型有哪些？| 强一致 / 弱一致 / 最终一致 / 因果一致 / 读己之写 |
