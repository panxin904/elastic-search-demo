# 📐 MySQL 垂直拆分 vs 水平拆分

> 当单库数据量达到瓶颈时（通常 > 5TB 或 QPS > 10万），就需要分库分表。选择正确的拆分策略是关键。

## 🎯 什么时候需要拆分？

```
MySQL 单库极限：
- 数据量：~2-5 TB（再大备份/恢复慢）
- QPS：~5-10 万（受单实例资源限制）
- 连接数：~1000-2000

如果你的业务：
- 单表 > 5000 万行
- 单库 > 2 TB
- QPS > 5 万
- 写并发 > 5000

→ 考虑分库分表
```

## 📊 两种拆分策略

### 1. 垂直拆分（按业务/列）

```
拆分前：
┌─────────────────────────────────┐
│           users                  │
│  id, name, email, avatar, ...   │
│  id, order_no, amount, items... │  ← 订单表
│  id, title, content, cover...   │  ← 文章表
└─────────────────────────────────┘

垂直拆分后：
┌──────────────────┐   ┌──────────────────┐
│  user_db         │   │  order_db        │
│  - users         │   │  - orders        │
│  - profiles      │   │  - order_items   │
└──────────────────┘   └──────────────────┘
┌──────────────────┐
│  article_db      │
│  - articles      │
│  - comments      │
└──────────────────┘
```

### 2. 水平拆分（按行/数据）

```
拆分前：
┌─────────────────────────────────────┐
│           orders (1 亿行)            │
└─────────────────────────────────────┘

水平拆分后：
┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  orders_0     │ │  orders_1     │ │  orders_2     │ │  orders_3     │
│  (2500 万行)  │ │  (2500 万行)  │ │  (2500 万行)  │ │  (2500 万行)  │
└──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
```

## 🎯 垂直拆分详解

### 适用场景

```
✅ 业务边界清晰
✅ 不同业务的访问模式差异大
✅ 某些字段特别大（TEXT / BLOB）
✅ 团队按业务拆分
```

### 拆分方法

```sql
-- 1. 按业务拆分（垂直分库）
-- user_db / order_db / product_db / payment_db

-- 2. 按列拆分（垂直分表）
-- 大字段单独成表
CREATE TABLE user_basic (
  id BIGINT PRIMARY KEY,
  username VARCHAR(50),
  email VARCHAR(100)
);

CREATE TABLE user_profile (
  user_id BIGINT PRIMARY KEY,
  bio TEXT,
  avatar_url VARCHAR(200)
);
```

### 优点 / 缺点

| 优点 | 缺点 |
|---|---|
| 业务清晰 | 跨库 JOIN 困难 |
| 不同业务独立扩展 | 分布式事务复杂 |
| 影响范围小 | 需考虑数据一致性 |

## 🎯 水平拆分详解

### 适用场景

```
✅ 单表数据量巨大（> 5000 万行）
✅ 写并发高（> 5000 QPS）
✅ 多数查询带分片键
✅ 业务能容忍最终一致性
```

### 拆分方法

#### 1. 按范围拆分

```
按 id 范围：
orders_0: id 1 - 1000万
orders_1: id 1000万 - 2000万
orders_2: id 2000万 - 3000万

按时间范围：
orders_2024: 2024 年的订单
orders_2025: 2025 年的订单
```

**优点：**
- 范围查询友好
- 新数据写入新分片

**缺点：**
- 数据可能不均匀（热点）
- 扩容需要数据迁移

#### 2. 按 Hash 拆分

```sql
-- 按 user_id 取模
-- 假设分 4 张表
orders_0: hash(user_id) % 4 = 0
orders_1: hash(user_id) % 4 = 1
orders_2: hash(user_id) % 4 = 2
orders_3: hash(user_id) % 4 = 3
```

**优点：**
- 数据均匀
- 简单

**缺点：**
- 扩容需要 rehash
- 范围查询需要扫所有分片

#### 3. 一致性 Hash

```
将分片组织成环，新节点加入只影响相邻分片
适合：分片数经常变化的场景
```

### 水平拆分的挑战

```sql
-- 1. 跨分片 JOIN
-- ❌ JOIN orders_0.user_id = users_0.id（要求 user_id 在同一分片）
-- 解决：把 users 也按 user_id 分片

-- 2. 分布式事务
-- ❌ 跨分片写入需要分布式事务
-- 解决：最终一致性、消息队列

-- 3. 全局排序
-- ❌ ORDER BY id 需要合并所有分片
-- 解决：按分片键排序

-- 4. 全局唯一 ID
-- ❌ AUTO_INCREMENT 不能保证全局唯一
-- 解决：Snowflake / UUID / 分布式 ID 生成器
```

## 🎯 分片键的选择

### 黄金法则

```
1. 高频查询条件 = 分片键
2. 业务核心字段 = 分片键
3. 避免热点 = 分片键分布均匀
```

### 案例 1：订单表

```sql
-- 选择 user_id 作为分片键
-- 原因：
-- 1. 80% 的查询都带 user_id（"我的订单"）
-- 2. 写也是按 user_id 分布（用户下单）
-- 3. 不会出现热点（用户 ID 是均匀的）

-- 4 个分片
orders_${user_id % 4}
```

### 案例 2：用户表

```sql
-- 选择 id 作为分片键
-- 直接按主键分片
users_${id % 4}
```

### 案例 3：日志表

```sql
-- 选择 created_at 作为分片键（按时间）
-- 优点：冷热数据分离
-- 缺点：当前时间分片会热

logs_${YYYYMM}  -- 按月分片
```

### 反例

```sql
-- ❌ 错误的分片键
-- 1. 用 status（只有 5 个值，不均匀）
-- 2. 用 is_deleted（0/1，极度不均）
-- 3. 用 country（某些国家数据特别多）
-- 4. 用 created_at 按天（最新的分片最热）
```

## 📐 拆分实战

### 案例：电商订单分库分表

```
分库：4 个
├── order_db_0
├── order_db_1
├── order_db_2
└── order_db_3

每个库 4 张表（共 16 张）：
├── order_db_0
│   ├── orders_0
│   ├── orders_1
│   ├── orders_2
│   └── orders_3
└── ...

分片规则：
- 分库：user_id % 4
- 分表：(user_id / 4) % 4
- 总分片数：4 * 4 = 16
```

```sql
-- 订单 12345 属于哪个分片？
-- 库：12345 % 4 = 1 → order_db_1
-- 表：(12345 / 4) % 4 = 3086 % 4 = 2 → orders_2
-- 最终：order_db_1.orders_2
```

## 📊 容量规划

```
业务目标：
- 5 年内订单总量：50 亿
- 平均每单数据：1 KB
- 总数据量：50 亿 * 1KB = 5 TB

分片规划：
- 每分片数据：< 500 GB
- 分片数：5 TB / 500 GB = 10 个
- 考虑冗余：实际 16 个分片

库表结构：
- 4 个库 × 4 张表 = 16 个分片
- 每分片 ~300 GB（满足 < 500 GB）
```

## 🛠️ 拆分的实施步骤

```
1. 评估现状
   - 单库数据量
   - QPS / TPS
   - 业务增长趋势

2. 选择拆分策略
   - 垂直 / 水平
   - 分片键
   - 分片数

3. 改造应用
   - 引入分库分表中间件
   - 修改 SQL（指定分片键）

4. 数据迁移
   - 全量迁移
   - 增量同步
   - 数据校验

5. 灰度切流
   - 双写
   - 对比
   - 切换

6. 监控验证
   - 数据一致性
   - 性能指标
   - 告警
```

## 🎯 总结

**拆分选择决策树：**
```
单库数据 < 2TB，单表 < 2000万
└── 不需要拆分，优化索引即可

单库 2-5TB，单表 2000万 - 1亿
└── 考虑垂直拆分（按业务/字段）

单库 > 5TB，或 QPS > 10万
└── 必须水平拆分（按分片键）

分片数计算：
- 当前数据 / 500GB = 最小分片数
- 5年增长预估 / 500GB = 未来分片数
- 取较大值，并预留 2-3 倍冗余
```

**核心原则：**
- ✅ 分片键 = 高频查询字段
- ✅ 分片数 = 2 的 N 次方（便于扩容）
- ✅ 单分片 < 500 GB
- ✅ 业务能容忍跨分片限制
