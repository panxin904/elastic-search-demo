# ❓ IoT 面试与常见问题

> 分 Easy / Medium / Hard 三档，覆盖协议、架构、嵌入式、安全。

## Easy（基础）

### Q1：MQTT 和 HTTP 相比有什么优势？

**答**：MQTT 是发布/订阅模式，专为低带宽、不稳定网络设计：

| 维度 | MQTT | HTTP |
|---|---|---|
| 协议开销 | 2 字节固定头 | 数百字节头 |
| 连接模式 | 长连接、心跳保活 | 短连接、请求/响应 |
| 网络要求 | 能在 3G / 卫星下工作 | 弱网频繁超时 |
| 实时性 | 推送（push） | 轮询（pull） |
| 主题路由 | Topic 通配符 | URL 路径 |
| 适用场景 | 设备 → 云、设备间 | Web / API |

物联网设备量多、带宽小、消息小（几十字节），MQTT 比 HTTP 节省 90%+ 流量。

### Q2：MQTT QoS 0/1/2 的区别？

**答**：

- **QoS 0**：at most once，至多一次，不重传、不确认。带宽最省，丢消息无所谓时用。
- **QoS 1**：at least once，至少一次，PUBACK 确认 + 重传。**最常用**，可能重复但保证到达。
- **QoS 2**：exactly once，恰好一次，四次握手（PUBREC / PUBREL / PUBCOMP），最可靠也最慢。

实际工程：99% 场景用 QoS 1；幂等性在应用层解决（带 messageId 去重）。

### Q3：什么是设备影子（Device Shadow）？

**答**：云端维护一个"虚拟设备状态"，包含 `desired`（期望状态）和 `reported`（实际状态）。

工作流：

1. App 设置 desired = { "switch": "on" }
2. 设备上线时拉取 desired，与自己 reported diff
3. 设备应用变更后更新 reported 上报
4. App 拉 reported 确认执行结果

**价值**：设备离线时也能"下发指令"（影子缓存），上线后自动同步；解耦 App 实时性与设备在线状态。

## Medium（进阶）

### Q4：MQTT Topic 应该怎么设计？

**答**：层级化 + 业务前缀 + 设备 ID：

```text
{tenant}/{product}/{deviceId}/{service}
```

示例：

```text
acme/factory-A/sensor-001/telemetry
acme/factory-A/sensor-001/event
acme/factory-A/sensor-001/command
```

设计原则：

- **不要超过 7 层**，影响通配符匹配效率
- **设备 ID 唯一**（用 IMEI / MAC / SN）
- **通配符**：订阅 `acme/+/sensor-001/#` 拿某设备所有消息；`acme/factory-A/#` 拿整厂
- **保留前缀**：以 `$SYS/` 开头是 MQTT broker 内部状态，客户端不能用

### Q5：边缘网关的价值是什么？为什么不全放云端？

**答**：边缘网关 4 大价值：

| 价值 | 说明 |
|---|---|
| 协议转换 | Modbus / CAN / 串口 → MQTT / HTTPS，云端只懂 IP 协议 |
| 本地缓存 | 网络抖动时数据不丢，恢复后批量上行 |
| 实时响应 | 工业控制 < 10ms，云端 RTT 不达标 |
| 带宽 / 成本 | 摄像头原始流本地预处理，云端只接元数据 / 告警 |

**反模式**：所有逻辑都放云端 → 一次断网全厂停产；所有逻辑都放边缘 → 设备端太重、难升级。

### Q6：InfluxDB / TDengine / TimescaleDB 怎么选？

**答**：

| 维度 | InfluxDB | TDengine | TimescaleDB |
|---|---|---|---|
| 数据模型 | Tag + Field + Timestamp | 超级表 + 子表 | PG 表 + hypertable |
| 写入吞吐 | 中（百万/秒） | 高（千万/秒） | 中（百万/秒） |
| 压缩比 | 5-10x | 10-20x | 5-10x |
| 查询语言 | InfluxQL / Flux | SQL | SQL |
| 部署复杂度 | 单进程 | 集群需 3 节点起 | PG 扩展 |
| 生态 | Grafana 一等公民 | 国产、Grafana 插件 | 与 PG 工具链通吃 |
| 适用场景 | 中小规模 / 通用 | 高写入 / 国产化 | 已有 PG 团队 |

**经验**：十万级设备 InfluxDB 够用；百万级以上 TDengine 性价比更高；团队 PG 强直接 TimescaleDB。

## Hard（架构 / 安全）

### Q7：千万级 IoT 平台怎么设计？

**答**：分层架构 + 关键组件：

```text
┌────────────────────────────────────────┐
│ 设备层（千万级）                            │
│   - MQTT 长连接、CoAP / LwM2M             │
│   - 设备 SDK（连接管理 + OTA + 影子）       │
└────────────────────────────────────────┘
           │ 百万并发连接
           ▼
┌────────────────────────────────────────┐
│ 接入层（EMQX 集群 / 自研网关）              │
│   - 负载均衡 + 多协议接入                   │
│   - 认证鉴权 + 限流                        │
│   - 消息路由（Kafka Pulsar）              │
└────────────────────────────────────────┘
           │ 千万 TPS
           ▼
┌────────────────────────────────────────┐
│ 流处理层（Flink / eKuiper）                │
│   - 规则引擎（数据清洗 / 告警 / 转发）       │
│   - 设备影子同步                           │
│   - 时序库写入                             │
└────────────────────────────────────────┘
           │
           ▼
┌────────────────────────────────────────┐
│ 存储层                                     │
│   - 时序库：TDengine / InfluxDB（设备数据） │
│   - 关系库：PostgreSQL（设备元数据 / 影子）   │
│   - 消息队列：Kafka / Pulsar（下行命令）     │
│   - 对象存储：S3（OTA 固件 / 大文件）        │
└────────────────────────────────────────┘
           │
           ▼
┌────────────────────────────────────────┐
│ 应用层                                      │
│   - 设备管理后台                            │
│   - 实时大盘（Grafana）                     │
│   - 告警与远程命令                          │
│   - 第三方 API（租户隔离）                  │
└────────────────────────────────────────┘
```

**关键决策点**：

- 千万级连接需要 EMQX 5.x 集群（至少 3 节点），单节点瓶颈在 ~200 万
- 消息总线必须异步：Kafka 主题按 `tenant` 分区，避免热点
- 时序库与关系库分离：时序数据生命周期短（30 天），元数据长期保留
- 多租户隔离：namespace + 资源配额 + RBAC
### Q8：OTA 升级怎么做才能保证"不变砖"？

**答**：5 个关键机制：

1. **差分升级**：bin diff（bsdiff / hdiff），从 10MB 全量降到 500KB 差分包，节省 95% 带宽
2. **断点续传**：HTTP Range + 分片 MD5，断网续传无需重头
3. **签名验证**：固件发布前用厂商私钥签名（RSA / ECDSA），设备端用公钥验签，防止中间人篡改
4. **A/B 分区**：设备 flash 分 A / B 两区，本次升级写到 B 区，重启切到 B；失败自动回滚 A
5. **灰度策略**：先 1% → 10% → 50% → 100%，每阶段观察 30 分钟异常率，异常率 > 阈值立即暂停

参考：AWS IoT Jobs / 阿里云 OTA / 华为云固件升级 都提供完整流程。

### Q9：IoT 设备安全从哪些层面入手？

**答**：4 层防护：

| 层 | 防护 | 技术 |
|---|---|---|
| 设备身份 | 每台设备唯一身份 | X.509 证书烧录 / TPM / SE 安全芯片 |
| 通信加密 | 链路不可被窃听 | mTLS（MQTT over TLS 1.3） |
| 平台鉴权 | 设备不能冒充云 | JWT / OAuth2 device flow |
| 数据完整性 | 指令不被篡改 | 消息签名（HMAC / ECDSA） |

**额外要求**：

- 关闭 MQTT `anonymous = true`
- 关闭不必要的端口（Telnet / 调试串口）
- 定期轮换证书（设备端支持 OTA 更新证书）
- 安全启动（Secure Boot）防止固件被替换

## 一句话总结

IoT 工程师的核心能力是 **"懂一点硬件 + 懂一点网络 + 懂一点云端"**，三段都懂才能做端到端设计；只懂一段容易被上下游卡脖子。
