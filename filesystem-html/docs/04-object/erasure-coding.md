# 纠删码 Erasure Coding — 用空间换安全的数学

> <span class="kg-badge kg-badge--object">对象存储</span>
> Reed-Solomon · k + m · 50% 空间冗余

副本策略最简单：数据写 N 份。但代价是**存储开销 100%（2 副本）到 200%（3 副本）**。

纠删码（EC）用数学手段把"冗余度"降到 **50% 甚至更低**，同时保留容错能力。它是 PB 级对象存储的核心技术。

## 1. EC 的核心思想

把一个对象切成 **k 个数据分片**，再算出 **m 个校验分片**：

```
k 数据片 + m 校验片 = k + m 总片数
任意 ≤ m 个片丢失可恢复
存储开销 = (k+m)/k
```

| 策略 | 配置 | 开销 | 容错 |
|------|------|------|------|
| 3 副本 | 1×3 | 200% | 2 盘 |
| EC 2+1 | 2+1 | 150% | 1 盘 |
| EC 4+2 | 4+2 | 150% | 2 盘 |
| EC 6+3 | 6+3 | 150% | 3 盘 |
| EC 8+4 | 8+4 | 150% | 4 盘 |
| EC 4+2 + 4+2 双层 | (4+2)×2 | 300% | **2 站点** |

EC 的本质：用相对小的空间开销换取高容错，并减少恢复时网络/IO 开销。

## 2. 数学原理：Reed-Solomon

最常见的 EC 实现是 **Reed-Solomon 码**（RS Code）。

### 2.1 加法 / 乘法

RS 在 **有限域** 上做运算（常用 GF(2^8) = 256 个元素），每个字节看作域中的一个元素：

- 加法：按位 XOR
- 乘法：查对数表（log/exp）+ 异或 / XOR

### 2.2 编码

把 k 个数据分片视为向量 D = (d1, d2, ..., dk)，乘以**范德蒙德矩阵**得到校验分片：

```
V = [I_k  |  P]   ← 生成矩阵（I_k 是单位阵，P 是校验生成块）
c_i = V_i · D      ← 每个分片 = 生成矩阵对应行 · 数据向量
```

### 2.3 恢复

丢失 ≤ m 个分片时，剩下 k 个分片依然能组成**线性方程组**，求逆得到原始数据：

```
[V]      [D]      [c1]
[ 子集 ] × [D] = [剩余校验]
[       ]  [D]      [cn]

→ D = V^{-1} × (剩余 c)
```

GF(2^8) 上的求逆存在且唯一（只要剩余分片 ≥ k 个）。

## 3. EC 在分布式对象存储里的实现

### 3.1 MinIO（k=4, m=2 默认）

```
对象 O = 64 MB（举例）

拆分：4 数据片 × 16 MB + 2 校验片 × 16 MB
分布：每个片写到不同 disk（甚至不同 host）
容错：任意 2 个片丢失（disk 故障），剩 4 片可恢复
```

MinIO 用 Intel ISA-L 加速，吞吐接近内存速度。

### 3.2 Ceph RGW（pool 内副本或 EC）

```bash
# 创建 EC pool
ceph osd pool create ecdata 64 64 erasure
ceph osd pool set ecdata crush_roots mydc

# 设置 rule
ceph osd crush rule create-erasure ecrule \
    mydc k=4 m=2

ceph osd pool set ecdata crush_rule ecrule
```

RGW 自动把对象切分到 EC pool。

### 3.3 HDFS EC（自 3.x 起）

```bash
hdfs ec -createPolicy -policy RS-4-2-1024k -replication 4 -parityUnits 2
hdfs ec -setPolicy -path /ecdata -policy RS-4-2-1024k
```

`1024k` = 一个 cell 大小 1 MiB。

## 4. EC vs 副本：对比表

| 维度 | 副本 | EC |
|------|------|----|
| 空间开销 | 100%+ | 50% 左右 |
| 容错 | 与副本数一致 | 与 m 一致 |
| 写延迟 | 低（写多份） | 较高（算校验） |
| 恢复时网络开销 | **巨大**（全量重传） | **小**（仅读 k 片） |
| 小对象 | 优 | 劣（celling 小会浪费） |
| 大对象（MB+） | 中 | **优** |
| 实现复杂度 | 低 | 高（需要 RS 编解码） |
| 适用场景 | 元数据、热数据 | 冷数据、海量数据 |

## 5. EC 的坑与最佳实践

### 5.1 小对象问题

如果对象只有 1 MiB 而 EC cell 是 1 MiB，那么：

- 1 个对象被切成 1 个数据片
- EC 4+2 还是占 6 × 1 MiB = 6 MiB

**浪费率 500%**！MinIO / HDFS 解决：把多个小对象打包成更大的条带（packing）。

### 5.2 恢复时的"重建风暴"

如果一次挂掉 2 个 disk：

- EC 修复需要读剩余 4 个 disk
- 同时 IO 加倍 → 影响业务 IO

**缓解**：修复限速、错峰修复（业务低峰期执行）。

### 5.3 选择 k 与 m

| 数据量 | 推荐配置 |
|--------|----------|
| < 1 PB | 4+2（容 2 盘） |
| 1~10 PB | 6+3 或 8+4 |
| > 10 PB | 8+4 + 多站点双层 EC |

### 5.4 不要 EC 临时数据

频繁写 / 删的数据 EC 编解码开销大 → 用副本反而划算。

## 6. EC 的数学直觉（白话版）

把 EC 想象成解方程：

```
x + y = 10   (校验片 1)
x + 2y = 14  (校验片 2)
```

只要知道 2 个方程，就能反推 x, y（数据片）。即使丢了一个方程，还有另一个能恢复。这**就是 RS(2,1) 的样子**：2 个校验位保护 1 个数据位。

推广：

```
k 数据位 + m 校验位 = k+m 总位
任意丢 m 位 → 还有 k 位 + 部分校验位 → 解出 k 个数据
```

## 7. 进阶：LRC / Locally Repairable Codes

标准 RS 是"全局"恢复：丢一个片要读其他 k 个。

**LRC** 把校验片分组，**局部就能修复部分丢失**：

```
RS(10,4)：丢 1 片，要读 10 个 → IO 巨大
LRC(10,2,2)：5+5 分组，每组独立校验，丢 1 片只读 5 个
```

Microsoft Azure Storage（WAS）就用 LRC。

## 8. 关键 Takeaway

| 要点 | 记忆口诀 |
|------|----------|
| k+m 总片数 | "k 数据 m 校验" |
| 空间 50% 开销 | "半价双保险" |
| Reed-Solomon = GF(2^8) | "RS=字节为域" |
| 恢复读 k 个 | "k 即可复原" |
| 小对象别用 EC | "小文件=副本划算" |
