# ❓ 游戏开发面试与常见问题

> 分 Easy / Medium / Hard 三档，覆盖引擎、渲染、网络、AI、性能。

## Easy（基础）

### Q1：Unity vs Unreal vs Godot 怎么选？

**答**：

- **Unity（C#）**：移动端 / 中小型游戏 / 跨平台首选，资源商店最全，迭代快
- **Unreal（C++ / Blueprint）**：3A / 主机 / 写实画面首选，光追 + Nanite + Lumen 内置
- **Godot（GDScript / C#）**：开源免费 / 2D / 独立游戏 / 学习成本最低

| 维度 | Unity | Unreal | Godot |
|---|---|---|---|
| 主要语言 | C# | C++ + Blueprint | GDScript + C# |
| 包大小 | 较小 | 较大（带引擎 ~150MB） | 很小（10-30MB） |
| 图形能力 | 中 | 顶级 | 中 |
| 平台覆盖 | 全平台 | 全平台（主机强） | 全平台（主机弱） |
| License | 订阅制 | 5% 营收抽成 | MIT 免费 |
| 学习曲线 | 平缓 | 陡峭 | 平缓 |

### Q2：什么是 Draw Call？怎么优化？

**答**：

Draw Call 是 CPU 向 GPU 提交的一次绘制命令。一次 Draw Call 包含：设置渲染状态 + 提交顶点 / 索引 + 切换 Shader / 纹理。

**优化方法**：

1. **合批（Batching）**：相同材质的网格合并为一个 Draw Call
   - Static Batching：静态物体编辑器期合并
   - Dynamic Batching：小动态物体运行时合并（顶点数 ≤ 300）
   - SRP Batcher（URP）：兼容 SRP 的合批
2. **GPU Instancing**：相同 Mesh + Material 的实例一次提交
3. **图集（Atlas）**：多张小图合成一张大纹理，减少纹理切换
4. **减少材质数量**：共享 Material 实例
5. **遮挡剔除（Occlusion Culling）**：不渲染被遮挡的物体

### Q3：什么是游戏循环（Game Loop）？

**答**：

游戏循环是游戏引擎的核心，每帧按固定顺序执行：

```
while (running) {
    processInput();     // 处理输入
    update(dt);         // 更新游戏状态（dt = 距离上一帧的时间）
    render();           // 渲染画面
}
```

**两种时间步长策略**：

- **固定时间步长（Fixed Timestep）**：逻辑更新用固定 dt（如 1/60s），物理稳定
- **可变时间步长（Variable Timestep）**：渲染跟显示刷新率（如 144Hz），画面流畅

**现代引擎做法**：逻辑固定步长 + 渲染可变步长 + 插值（Interpolation）补偿。

## Medium（进阶）

### Q4：状态同步和帧同步的区别？

**答**：

| 维度 | 状态同步 | 帧同步（Lockstep） |
|---|---|---|
| 同步内容 | 客户端状态变化 | 操作指令（Input） |
| 网络带宽 | 中（按状态变化频率） | 低（只传输入） |
| 服务器职责 | 权威转发 / 仲裁 | 只转发输入 |
| 客户端负担 | 中 | 重（必须确定性回放） |
| 一致性 | 服务器仲裁 → 强一致 | 确定性 → 天然一致 |
| 反外挂 | 容易（服务器有全量） | 难（客户端决定结果） |
| 适合 | FPS / MOBA / 回合制 | RTS / 格斗 / 棋牌 |
| 代表作 | 王者荣耀 / LOL | 魔兽争霸 3 / 星际争霸 |

**关键点**：

- **状态同步**：服务器收状态变化 → 广播给其他客户端；服务器可校验 / 仲裁
- **帧同步**：所有客户端收到相同输入 → 各自独立模拟 → 靠确定性保持结果一致
- **混合**：常见做法是 RTS 用帧同步，关键事件用状态同步兜底

### Q5：什么是客户端预测（Client Prediction）？

**答**：

客户端预测是为了解决网络延迟导致的"操作卡顿"问题。

**核心思想**：客户端不等服务器确认，立即按本地输入执行，并预测结果；服务器仲裁后若有差异，客户端回滚 + 重新应用未确认的输入。

**三步流程**：

1. **预测执行**：客户端收到输入 → 立即本地执行 → 显示结果
2. **服务器确认**：服务器收到输入 → 执行权威逻辑 → 返回结果
3. **客户端对账**：客户端收到服务器结果 → 与本地预测对比 → 不一致则回滚并重放

**配套技术**：

- **插值（Interpolation）**：其他玩家位置 / 状态平滑插值（100-200ms 延迟渲染）
- **Lag Compensation（服务器侧）**：服务器回溯时间点做命中判定

### Q6：A* 算法和 NavMesh 寻路有什么区别？

**答**：

- **A\***：基于图的启发式搜索，作用于网格（Grid）图；适合规则地形
- **NavMesh**：将可行走区域烘焙成凸多边形网格，搜索作用于多边形；适合复杂不规则地形

**算法对比**：

| 维度 | A* | NavMesh |
|---|---|---|
| 图结构 | 网格 / 四叉树 | 凸多边形 |
| 内存占用 | 较高（节点多） | 较低（区域聚合） |
| 路径质量 | 锯齿状 | 平滑 |
| 动态障碍 | 需重算 | 局部重规划 |
| 适合 | 室内 / 网格地图 | 开放世界 / 不规则地形 |

**实战建议**：开放世界用 NavMesh，室内 / 棋盘用 A\*；寻路开销大时考虑 Flow Field（流场，一次计算全场）。

## Hard（高级）

### Q7：前向渲染和延迟渲染的取舍？

**答**：

**前向渲染（Forward Rendering）**：

- 几何阶段：所有光照在顶点 / 像素着色器一次性计算
- 优点：支持 MSAA、半透明、抗锯齿友好、低带宽
- 缺点：光源数 = 几何复杂度 × 光源数（O(G × L)）

**延迟渲染（Deferred Rendering）**：

- 第一遍：G-Buffer（Position / Normal / Albedo / Material）写入 MRT
- 第二遍：用 G-Buffer 做光照计算（每个像素只算可见光）
- 优点：光源数与场景复杂度解耦（O(G + L)），适合大量动态光
- 缺点：带宽大、不支持 MSAA、半透明物体需额外 Forward Pass

**现代方案（Clustered / Tiled Forward+）**：

- 把屏幕分块（Tile）或按深度切片（Cluster）
- 每个块的光源列表预先计算
- 前向管线 + 大量光源，兼顾带宽和透明

**选型决策**：

- 光源 ≤ 4 个 → 前向
- 光源 ≥ 8 个 + 动态阴影 → 延迟
- 移动端 / 带宽敏感 → Forward+ 或 Clustered

### Q8：如何排查游戏内存泄漏 / GC 卡顿？

**答**：

**内存泄漏排查**：

1. **Profiler 抓快照**：Unity Profiler / Unreal Memory Insights
2. **对比基线**：场景切换前后内存不下降 → 泄漏
3. **常见泄漏点**：
   - 静态集合未清理（`static List<T>`）
   - 事件订阅未解绑（C# event -= handler）
   - Unity Resources / AssetBundle 未 Unload
   - 单例持有 DontDestroyOnLoad 对象引用

**GC 卡顿排查**（Unity C#）：

1. **开启 GC Profile**：`Profiler` → `Memory` → `Allocation Call Stacks`
2. **定位大对象分配**：`>1KB` 的数组、字符串拼接
3. **优化方法**：
   - 用 `StringBuilder` 替代 `+`
   - 用对象池（ObjectPool<T>）复用
   - 用 `struct` / `值类型` 替代小 class
   - 避免 LINQ（隐式装箱）
   - 用 `ArrayPool<T>` 复用数组
   - 用 `unsafe` / `NativeArray` 绕过 GC

**Unreal**：UObject 自动 GC，但 UPROPERTY 标记的对象不会被回收（类似引用计数）；用 `obj list` 命令查看活跃对象。

### Q9：如何设计一个高一致性的多人竞技同步系统？

**答**：

**目标**：所有客户端在 ≤ 100ms 网络抖动下，看到一致结果。

**核心设计**：

1. **同步模型选型**
   - FPS / MOBA → 状态同步 + 服务器权威
   - RTS / 格斗 → 帧同步 + 确定性模拟
   - 回合制 → 状态同步即可

2. **关键模块**
   - **客户端预测**：本地立即响应，服务器仲裁回滚
   - **服务器侧 Lag Compensation**：命中判定回溯客户端时间点
   - **实体插值**：其他玩家位置 100-200ms 延迟渲染 + 平滑插值
   - **确定性随机**：所有客户端用相同种子 RNG（避免飘字）
   - **Tick Rate**：30 / 60 / 128 Hz，越高越流畅但带宽越大
   - **回放录像**：记录输入流，本地可复现任意时间点

3. **反作弊**
   - 服务器权威（所有伤害 / 得分服务器计算）
   - 协议加密 + 签名（防抓包伪造）
   - 行为检测（自瞄 / 透视 / 加速）
   - 客户端完整性校验（反调试 / 反注入）

4. **网络优化**
   - UDP + 自研可靠层（KCP / ENet）
   - 状态变化频率限制（Rate Limiting）
   - 兴趣区域（AOI / Area of Interest）：只同步视野内实体
   - 数据压缩（位运算 / protobuf）

5. **调试工具**
   - 服务器 / 客户端同步录像回放
   - 网络模拟器（丢包 / 抖动注入）
   - 时间戳 + Replay 系统
